# Agent

The `agent.garam.sh` API group, the `Agent` kind it serves, and the controller that reconciles it.

## Current decisions

- `Agent` is served at `agent.garam.sh/v1alpha1` and is namespaced. Its types live in `api/v1alpha1/` and its reconciler in `internal/controller/` — the paths the kubebuilder CLI owns.
- An agent's desired definition — what it runs with, the templates it is made from, and the revisions of both — is owned by this project's control service, whose store is the one place it is written. `garam` owns the agent's stable identity, its GRN, together with organization authorization and collaboration, and the manager renders each `Agent` from the control store. Each GRN takes its desired state from one of two sources, and `spec.identity.source` says which: `Garam`, a definition this operator claims from `garam` and builds an `Agent` from as the decisions below describe, or `Control`, the control service's desired feed. Absent reads as `Garam`.
- For every `Agent` on the `Control` source the manager renders the spec from the control service's feed on every new revision: model, ego, tools, the profile's resources, storage size and storage class, the assignment epoch, and the operator's image. A hand edit to one of those is reverted at the next revision. On the `Garam` source only `spec.image` is kept current after construction, as below, and every other field is written once, until garam#1171 switches the GRN. An `Agent` with no GRN is not rendered from anything.
- The manager pulls the feed (`internal/desired`) only where `--control-address` is set, over mutual TLS as its own certificate, verifying the control service against `--control-trust-file`. It holds the cursor in memory and renders only a revision it has not already rendered.
  - **Status.** It reports each rendered revision as observed and rendered.
  - **Transient errors.** A 500, a 503 or no answer is asked again after a wait doubling from 1 to 30 seconds.
  - **Refusals.** Any 4xx, including 422 `too_many_agents`, is asked again only every 5 minutes. It is counted in `garam_operator_control_refusals_total{route,status}` and shown in `garam_operator_control_feed_refused`.
  - **Withheld agents.** An agent the feed stops naming keeps its `Agent`: rendering deletes nothing.
- A GRN the feed names with no `Agent` is a managed agent, which never reaches the `garam` poller (`garam@9afd0bf:api/machine.yaml:240-246`). Its `Agent` is constructed by the feed, with source `Control` and the names the GRN derives, and it waits as `CredentialsSecretMissing` until its first certificate is placed, as below. The source moves only from `Garam` to `Control`, which the API server enforces. The renderer refuses an `Agent` on any other source, so no GRN is rendered from both.
- A model's key reference from the feed is `<secret-name>/<key>` in the `Agent`'s namespace, the name a DNS subdomain and the key `[-._a-zA-Z0-9]+` and neither `.` nor `..`, as Kubernetes requires of a Secret's name and data key (`k8s.io/apimachinery@v0.36.0` `pkg/util/validation` `IsDNS1123Subdomain`, `IsConfigMapKey`). A malformed one leaves that revision unrendered and unreported. The control service refuses the same references before storing one (its `definition.SecretRef`). The rule is stated on each side rather than shared, because the manager imports nothing of the control binary.
- A managed agent's first certificate is asked of the control service by the issuer (`internal/desired`, a `Runnable` beside the puller, only where `--control-address` is set), at `POST /v1/operators/self/agents/{grn}/certificate-requests` (#218). `garam` signs it over a key this operator generates. Every second the issuer reads from the cache which `Agent`s on the `Control` source have no credential Secret.
  - **Persisted first.** It generates an ECDSA P-256 key and a request with an empty subject and no SAN, and persists both, with the epoch and the request id, in `<agent>-credential-request` before sending anything. That Secret is owned by the `Agent`, mounted nowhere, and read uncached through the API reader. The key is PKCS#8 in a `PRIVATE KEY` block, as `garam`'s own mint writes `key.pem` (`garam@7ca51b9` `internal/ca/service.go:110,116`).
  - **The request id** is `hex(sha256(CSR DER ‖ 0x00 ‖ epoch))`. A manager stopped anywhere resumes with the persisted key, request and id and is answered the stored result. No second key is generated while one is persisted.
  - **Placed whole.** Only a 201 or 200 naming the agent and the epoch asked creates the credential Secret, in one create, with the key beside the certificate, issuer and server root under `internal/garam`'s key names. The workload is then built once, with everything, and copied as ADR 0010 says. The request Secret is deleted after that create, or on the next pass where a stop came between the two.
  - **A superseded epoch** (409 `epoch_superseded`) keeps the key and the request: control refuses before `garam` signs anything, so no certificate exists over the key. The epoch is re-read from `spec.identity.assignmentEpoch`, which the feed renders, and a new one is persisted and sent as a new request under a new id. An unchanged epoch is asked again only after the long wait.
  - **Other refusals** (403, 409 for a changed request, 400) are counted in `garam_operator_control_refusals_total{route="certificate_requests",status}` and asked again, unchanged, only every 5 minutes. A 400 for a request this code built is a defect to surface, so nothing is regenerated around it. A 5xx or no answer is asked again after a wait doubling from 1 to 30 seconds.
- Moving where a definition is held changes no name: the `Agent`, its StatefulSet and its volume claim stay named for the digest of the GRN, so no migration re-creates a workload or detaches the volume the memory store is on. No new GRN is minted for an agent that has one, and the assignment epoch stays `garam`'s.
- Every connection leaves the cluster this operator runs in. No broker stands between the manager and the control service, and `garam` relays nothing between them.
- The supported scope is agents with an identity in `garam`, on one cluster, of the `sherlock` type. One cluster running one operator is what is supported, though nothing here prevents a second; `claude-code` and `codex` are on hold, admitted and refused as below. A hand-written `Agent` is for development and bring-up only: it is reconciled, but it has no GRN, no certificate `garam` issued for it, and no report reaches `garam` about it, so `garam` does not see it. The scope is stated, not enforced — nothing refuses what lies outside it.
- `AgentSpec.Type` names the agent binary the workload carries. It is optional, defaults to `sherlock`, and is validated at admission against the closed set `{sherlock, claude-code, codex}`. An unknown type is refused at admission by the kubebuilder validation; an admitted type that this controller version has not yet learned to build is refused on reconcile with `Synced=False, Reason=TypeUnimplemented`. The kind itself is unchanged — `Agent` is the generic name, and the type decides every name the Pod builder writes that is the agent binary's. Adding a new agent binary is a code change, with a new entry in the controller's per-type table; it is not a configuration change.
- The type's descriptor carries every such name, and the Pod builder reads them from it: the credential's two mount paths, the state volume's mount path, the memory store's path under it and the variable the agent reads it from, the configuration directory, the variable the agent reads it from, and the config file's path under it, the text the file renders to, the variable the model's key is placed in, the ego file's path, the agent's command line, the workspace's address and its four variables, and the gateway's address `garam`'s adapter dials. For `sherlock` each is cited to `sherlock@8218189:docs/architecture/deployment.md` at the field that holds it. Every field is required, and a type whose descriptor leaves one unset is refused with `TypeUnimplemented`, as `claude-code` and `codex` are. What every type shares stays out of it: container and volume names, the Pod's user, group and security context, the credential's modes, pull-always, and the owner-only mask.
- `AgentSpec` carries what an agent needs to run: the container image, the Secret its credential material comes from, the persistent volume it keeps state on, the compute resources its container asks for, and optionally its tool set, its model, its ego and its identity. `AgentStatus` carries observed state only, and nothing a user writes.
- The agent's memory store is on the volume its state is claimed on. This operator writes its path into the agent's environment on every Pod, absolute and one directory below the volume's mount; for `sherlock` the variable is `SHERLOCK_MEMORY_PATH` and the file `memory/memory.db`. `sherlock`'s default is relative and resolves against its image's working directory, on the container's own filesystem, so an agent left to it keeps its store in the Pod and loses it with the Pod. The store has a directory of its own because `sherlock` derives its outbox beside it: the two share one subtree of the volume, disjoint from the workspace's.
- The image reference is required and has no default. No registry or tag convention exists for the agent image and neither project owns one, so the field asks rather than invents; a default can be added later to a field that already exists. Who it asks is the operator's deployer and not the agent's author: an agent's definition says what the agent is, and what container that is built from is this operator's to decide.
- Every container of an agent's Pod pulls its image at every start. `sherlock` requires a consumer of its images to reference a digest and pull always (`sherlock@04ed05a:docs/architecture/adr/0020-immutable-image-repositories.md`), and this operator is that consumer: the repositories holding `sherlock`'s bring-up builds are emptied once a release path publishes, and the orchestrator's default leaves what that breaks as a stale cache on whichever nodes hold one, presenting as those nodes' fault rather than as one refusal every replica meets. The init container's image is not `sherlock`'s and that record does not reach it; it is pulled the same way on a ground of this operator's own — the image comes from this operator's configuration and nothing here requires its tag to name one build, so a node's cache would leave two agents' credentials copied by different tools under one name. What it costs is that an image no registry serves cannot be run, whatever put it on the node.
- `spec.image` accepts a tag and says what the holder of one is accepting, rather than requiring the digest half of that obligation. The field names any image and this operator owns no registry the requirement could rest on, so a refusal would fall on references `sherlock`'s record says nothing about — the image a constructed agent is given among them, which arrives from a flag no schema reaches and would be refused when a claimed definition's `Agent` was created rather than when the operator started. What a tag costs is stated where its holder reads it: pulling at every start makes a moved or emptied tag a restart that runs different bytes, the same on every node rather than a difference between them.
- Credential material is referenced, never carried. The Secret is created outside this operator, and the workload mounts its keys as files — the credential does not travel through environment variables. A model's API key is the one key that does, because its reader accepts nothing else; see below.
- The Pod carries a supplementary group, and the Secret is projected readable by that group rather than by its owner alone. A Secret volume's files are owned by root, so an owner-only mode leaves them unreadable to a container that drops root — and the operator cannot know which uid an arbitrary image runs as. A group needs no such knowledge: the kubelet puts every volume of the Pod under it and hands it to each container's initial process, whatever user that container runs as. It reaches no further on its own — a descendant that drops its supplementary groups leaves the group behind, and the credential with it. The same group is what makes a freshly provisioned state volume writable where the provisioner does not hand it over. Measured on 2026-08-24, on a volume a `csi.proxmox.sinextra.dev` StorageClass provisioned: the mounted directory is owned by root at mode 2775 with the Pod's group, and the container's own uid, which is neither root nor that gid, writes to it.
- The agent does not read that projection. `garam`'s adapter is what reads the agent's private key, in a sidecar of the agent's pod, and it refuses a key file any group or other bit is set on and refuses one owned by another user (`garam@1ff8346:internal/keyfile/keyfile.go:30-41`); `garam` publishes both halves as a deployment contract and refuses to relax them (`garam@1ff8346:docs/architecture/deployment-contract.md` §What the binary enforces about key material). A volume the kubelet writes satisfies neither half — the tightest mode it delivers under the group is `0440`, and the owner is root whatever is asked for.
- So an init container copies each projected file into a memory-backed volume the kubelet does not write, at a mode only its owner can reach, and the agent mounts that copy and not the projection. The group is what lets the init container read the projection, and memory is what keeps the copy off the node's disk.
- The Pod names one user and every container runs as it, so the copy's owner is whoever reads it. The operator names that user rather than being told it: an owner is one value for a whole Pod, and a uid taken off any one image stops being that value as soon as a second image in the Pod reads the same file. What an agent's image owes in exchange is stated on `spec.image`, where a user of the API reads it.
- The image the init containers run is this operator's own configuration and is required of every deployment, because every agent's Pod carries the one that places the credential — an `Agent` a user wrote as much as one this operator constructs. It needs a shell, `install` and `mkdir`, and nothing of the agent; the agent's own image cannot stand in, `sherlock`'s being distroless (`sherlock@e9c12a5:build/agent.Dockerfile`).
- What that gives up: an agent image that cannot run as the user the Pod names cannot be run at all, where a group asked nothing of the image; and any container of the Pod reads the copy, because they all run as its owner. The workload has two containers beside the init containers, and which of them mount that volume is the operator's to decide: the workspace does not, because it reads no credential.
- The copy is made once, at pod start. A credential replaced in the Secret afterwards reaches the projection and not the file the process reads, so replacing one is a restart.
- The workload is a StatefulSet of one replica with a volume claim template for the agent's volume.
- The workload is one a namespace enforcing PodSecurity `restricted` admits. The Pod asserts `runAsNonRoot` beside the user ADR 0010 named — naming a user the standard would accept is not the same as asserting one — and names the runtime's default seccomp profile; each container drops every capability and the right to gain a privilege. Those are the four the standard asks for and the four it refuses a Pod without, and none takes anything from a workload of this shape: the init containers run `install` and write a file, the agent runs whatever it runs, and the workspace executes its children through a path that asks for no capability at a non-root user. What they ask of an agent's image is stated on `spec.image`, and no flag offers any of them — the audience for one is the deployer already told the image must run as uid 65532. Measured on `garam-dev` on 2026-08-26, in a namespace labelled `pod-security.kubernetes.io/enforce=restricted`: the workload this operator builds was admitted and its Pod ran, with the credential arriving at mode 600 owned by the uid that read it; the same workload without those four fields had its Pod refused on all four, so what is admitting it is the security context and not the namespace.
- `readOnlyRootFilesystem` is set on none of the Pod's containers. It is no part of `restricted`, so nothing refuses the workload without it, and it is the one field of the Pod's security context this operator has not decided.
- An Agent's name is bounded at 52 characters, and the API server is what refuses a longer one. The workload's Pods carry that name with a suffix in a label — the longest is the revision hash, up to 11 characters — and a label value stops at 63. A name the API server took and the workload could not use would leave the controller building a StatefulSet whose Pods the API server then refuses, with nothing to retry.
- An Agent whose credentials Secret is absent gets no workload at all, and the Secret's arrival is what builds it. The Secret a model's key comes from is waited for the same way, reported as `ModelKeySecretMissing`, since a variable taken from a Secret that does not exist leaves the container unable to start just as a missing volume does. Mounting a Secret that does not exist leaves the Pod unable to start, and creating that Secret is not an edit to the Agent, so the controller watches the Secret rather than waiting to be woken by a spec change.
- No field of `v1alpha1` names an external system. What the operator needs to reach `garam` is process configuration — the machine listener's address, the certificate the operator authenticates with, that certificate's key, and the file the listener is verified against — and an unset address leaves it making no outbound call at all.
- The operator reads the definitions `garam` holds for it on an interval and claims each one `garam` holds no claim for. The read is scoped by the certificate the connection authenticated as, so it names nothing this operator is not named in. The poll runs beside the reconcilers as a manager `Runnable` and not inside one: the clock wakes it and no event on an `Agent` does.
- The certificate the operator authenticates with is read at each handshake, and each call opens its own connection so that there is one. Expiry is the whole of `garam`'s revocation, so a certificate loaded once stops authenticating on a schedule. What rewrites it is the operator itself, by renewing.
- That credential lives in one place: a Secret mounted into the manager's Pod, read as files and replaced through the API server. The Pod carries the same supplementary group the agent's workload does and the volume is mounted group-readable, because the kubelet writes those files as root whatever user the container runs as. Nothing copies the credential from a delivery into a working file, so nothing can seed it a second time and lose a renewal. Two things write it: this operator, which enrolls for a certificate wherever it holds none that has not expired and renews every one it holds in time, and the out-of-band mint, which is the recovery and what takes the lineage back.
- The read path and the write path are different on purpose. The operator learns its credential from the mounted file and reaches the API only to write a renewal, so it holds `patch` on that one Secret by name and neither `get` nor `list`. Both keys move in one patch, because a handshake reads a certificate beside the key it was issued with.
- The operator obtains its first certificate itself, by presenting a one-time token a person minted by registering it. It generates an ECDSA P-256 key pair in the cluster and sends a PKCS#10 request over it; `garam` reads the public key and the signature proving this operator holds the private half, discards everything else in the request, and answers a certificate and no private key, because it generated none. What the certificate names comes from the token, and the answer's GRN is where this operator learns its own identity.
- A token is one attempt and not one certificate: it is spent by the call that presents it whether or not that call goes on to succeed. So the request's own signature is verified here before anything is sent, and no token is presented twice — spent, expired and never-minted are one answer nothing here tells apart, and what recovers any of the three is another token rather than a retry.
- The enrollment call presents no certificate, because an operator enrolling has none to present, and verifies `garam` against the same file every other call verifies it against. The server root the answer carries is not what authenticated the answer, and neither it nor the issuer that signed the certificate is stored. That root is compared against the file that did authenticate it and a difference is named in one line, because nothing rewrites that file and a root `garam` has moved on from goes on working until every handshake fails at once.
- The token arrives as a key of the Secret the credential lives in. It is read at the attempt, held nowhere, logged nowhere and written to nothing, and what comes back is written through the store a renewal is written through, so the renewal reads what the enrollment wrote. An operator with no token there, or one already holding a certificate that has not expired, enrolls nothing and behaves as it did before.
- Enrollment waits for a token and ends on a certificate that has not expired, as a third `Runnable` in the leader-election group. An operator is deployed before it is registered, so the token is placed while the process is already running and waiting is what keeps that from needing a restart; two processes spending one token would leave one of them holding nothing.
- What the guard reads is the certificate's validity and not whether a file parses. A certificate that expired authenticates no call, so the renewal that would replace it is refused for presenting it, and an operator that counted it as an identity would close the only route left to it. Expiry is measured past `notAfter` on this operator's own clock with no margin allowed for skew: a margin spends a token to replace a credential `garam` still admits, and its absence costs at most that skew in delay. Everything before that instant is the renewer's.
- A refused token leaves that `Runnable` looking at the same file rather than ending it, so a replacement placed in the Secret is presented on the next look and no Pod is restarted to reach it. What holds the spent one back is the digest of every token this process has presented, kept in the process and written nowhere; it does not survive a restart, and a restarted operator re-presents a spent token once before it waits.
- The renewal runs beside the poll as a second `Runnable` and not inside it: the two answer to different clocks, and a call one makes should not hold the other's up. Both join the manager's leader-election group, and for the renewal that is load bearing rather than tidy — `garam` renews the certificate it last issued and refuses every other, so two processes renewing one identity leave the loser holding one it can never renew again. One identity is held by one process.
- The operator does not compute the renewal window; it asks on an interval and reads the kind of what comes back. A refusal meaning "too early" is not a failure, one meaning "superseded" is reported as needing a mint out of band, and nothing here restates the fraction `garam` measures the window by. The interval sits far below that window and far above the delay between a renewal being stored and the process reading it back.
- A certificate the window closed on fails at the handshake and stops nothing. The poll goes on failing and saying why, and the renewer says which refusal it met; a poller stopped instead would remove the only signal.
- That signal is carried as metrics as well as log lines, on the endpoint the manager already serves and through the registry controller-runtime owns. The names and labels are a stable surface an alert is written against:
  - `garam_operator_certificate_not_after_timestamp_seconds` is the `notAfter`, in Unix seconds, of the certificate this operator last read to authenticate with. It is set wherever the pair is loaded — at startup, at every handshake, at each look the enroller takes — so it follows a renewal at the next handshake, and it exports nothing until a certificate has been read.
  - `garam_operator_refusals_total{runnable, kind}` counts every refusal `garam` answered. `runnable` is `poller`, `renewer`, `reporter` or `enroller`; `kind` is `handshake` for an alert `garam` sent at the handshake, or the HTTP status it answered.
- What is counted is `garam` refusing and not this operator failing: a listener it did not verify or did not reach, a certificate it could not read and an answer it could not decode are not counted. A renewal refused as too early is not counted either — it is not a failure, and it shares status 409 with "superseded". No local check can stand in for the counter: a certificate whose authority `garam` no longer holds passes expiry, chain and root checks alike, and the refusal is the only thing that knows.
- The renewal follows the address rather than a Secret named beside it. The Secret is the one the manager's own Pod already mounts, so the deployment names it once and not twice, and an unset address leaves this operator renewing nothing as it leaves it reading nothing. The volume is optional, so a deployment given no identity still starts.
- What the listener is verified against is a file the deployment supplies, and not the organization issuer an operator's own certificate arrives beside: that authority signs this operator and a different one signs `garam`. It holds whatever `garam` presents, and what that is has already moved once: the leaf `garam-dev` served until 2026-08-26, and since then a `garam` machine server root that signs it and is a separate certificate. The flag is named for its role so that only the file's contents move, which is what happened. Verification is never skipped, under a flag or otherwise.
- A claim `garam` refuses as a conflict is terminal. A definition is claimed once, so nothing retries the refusal and the next read reports the definition as claimed.
- A desired definition says what the agent is and this operator says how an agent is built. What the agent is belongs to the control service's store; at present it arrives as a `garam` definition's values, whose keys `garam` stores and interprets none of, and publishes no list of. Construction is this operator's: the image, the storage size, the security context, the scheduling. So `AgentSpec` keeps `image` and `storageSize` required and the operator supplies them: no field of a desired definition a member edits names either, and no value of a `garam` definition does. What decided that beyond the division is that a console user choosing an agent's container is choosing what this operator runs as a root-capable workload in a cluster they cannot see, and `v1alpha1` carries no override for one.
- At present a `garam` definition's values carry what this operator can deliver, and the operator reads a closed set of keys out of them rather than carrying the map. That set holds one key family today: an agent's tool set, declared as one key per tool naming that tool's pin, with the pin opaque to this operator and the key name its contract. The key family is declared in the control store's desired definition once the manager pulls from it; what a pin set is and how it reaches the Pod, below, does not move with it. `values` is free-form and `garam` refuses no key, so an operator that carried the whole map would leave the prohibition on reading an image resting on nobody typing one. What the closed set costs is that a definition declares only what this operator has been taught, which is the cost `AgentSpec` already pays. The keys are read where `garam`'s answer is parsed and travel on as a typed selection, so no part of this operator downstream of that parse holds the map.
- The directory an agent loads its tools from is declared in no value, and this operator does not write it either. The agent's image carries its first-party tools and sets `SHERLOCK_TOOLS_DIR` to where they are (`sherlock@35e79b5:build/agent.Dockerfile:74-77`), so the directory is the image's and a variable written here would only override it. A definition naming it would point the agent at a directory whose contents its author controls, which is why it stays out of the keys a definition's values carry. The container's `command` is left unset as it always was, so the image's entrypoint is what runs; its `args` carry the agent's identity and, where declared, its ego, as below.
- Which tools an agent has follows from the build `--agent-image` names, and this operator builds no tool tree into the Pod: no image volume, no mount and no variable. A cluster changes its agents' tool set by naming another build. A workload an operator that still named a tools image built loses the tree on the next reconcile, because the Pod's volumes, the agent's mounts and its environment are written whole on every pass.
- The process an agent's files and commands are served by is a second container of the same Pod, running an image this operator's configuration names. `sherlock` splits the two deliberately: the agent's image is distroless and carries no shell, and an Exec child is `sh -c`, so running the workspace out of the agent's image fails at the first call. The agent executes nothing itself and reaches that process over the Pod's loopback interface.
- Both ends of that link are written by this operator rather than left to the two images' defaults. The workspace is told where to listen and the agent is told the same place to dial, at a loopback address — the only bind `sherlock`'s listener accepts while it carries no authentication. The two images already default to the same number, so nothing changes today; what changes is that the agreement is this operator's, where two defaults agreeing is not one number chosen and neither image moving its own would be noticed here.
- The workspace is told to run exec children as the user the Pod names. `sherlock` runs a child under its own account only where that number matches the uid it already has and refuses every isolated exec otherwise, and the two are made equal in that direction because the Pod's user is a number this operator chose with a recorded reason while the image's is one the image chose. No container names a user of its own.
- It serves a directory on a claim of its own, `workspace`, which only its container mounts, at the path the agent mounts its state at, so the directory is `/var/lib/sherlock/workspace` and the agent's memory path does not exist in that container. The default it would otherwise take is relative and resolves, in an image that declares no working directory, against a root-owned directory the Pod's user cannot create in — so the container would exit before it listened.
- The agent's state — the memory store and the outbox beside it — is on the `state` claim, which only the agent's container mounts, so code the agent runs cannot read or overwrite it (ADR 0044; `sherlock@44aaa55:docs/architecture/deployment.md` §Volumes and ownership, "Two writable volumes, not one shared filesystem"). Both claim templates are built whether or not a workspace image is named. The workspace's is sized by `spec.workspaceStorageSize`, and at `spec.storageSize` where that is unset; an `Agent` this operator constructs from `garam` takes it from `--agent-workspace-storage-size`, and the control profile does not carry it yet. Both use `spec.storageClassName`, and a size either claim cannot follow is reported as `StorageSizeImmutable`.
- A StatefulSet whose workspace shares the state claim is replaced only where the manager's `--agent-migrate-shared-claims` is on (ADR 0047). With it off, which is the default, such a StatefulSet is reconciled in the shape it has: the workspace keeps its mount on the state claim, no claim template changes, and nothing is seeded. Until it is replaced, the code that agent runs can still reach its state, and the `Agent` reports `StateIsolated` `False`, reason `SharedClaim`, which the `Isolated` column of `kubectl get agents` shows. A StatefulSet created where none exists always gets the separate shape, the flag on or off. The lab order is: roll the manager, suspend each shared-shape agent (#254), copy its state, turn the flag on, then clear the suspension. With the flag on, a shared-shape StatefulSet is deleted with propagation `Orphan`, leaving its Pod and its claims, and `Synced` reads `WorkloadReplacing` until it is gone; the next one adopts the old Pod and rolls it, and ADR 0042's fence holds that Pod until its writers stop. The `state` claim keeps its name, so it is the claim the agent keeps. A StatefulSet created where the `state` claim exists and the `workspace` one does not carries `agent.garam.sh/workspace-seed` and an init container, `workspace-seed`, which copies `workspace/` off the state claim, read-only, onto the new claim once — a copy, never a move, marked done only after a sync — and is a no-op on every later start.
  - **What an upgraded agent keeps.** The `state` claim keeps the whole stored state: `memory.db`, its `-wal` and `-shm`, and `outbox/` beside them (`sherlock@44aaa55:docs/architecture/deployment.md` §Snapshot and restore, "What the stored state is"). A check after the upgrade names all four, not `memory.db` alone.
- How a person reads or copies an agent's state now that only the agent's container mounts it:

On an upgraded set, only the `workspace-seed` init container mounts it, read-only, and it runs to completion before the agent starts.

      - an ephemeral container mounting `state` read-only was admitted;
      - one naming a volume the Pod lacks was refused as not found;
      - a `subPath` mount was refused as forbidden.
    - That is admission only: no kubelet runs there, so the mount itself was not observed.
    - Whoever may update `pods/ephemeralcontainers` can therefore read the running agent's state. What they read is a store its writer is still changing, so it is never a copy. ADR 0044's boundary is against the code the agent runs, not against a cluster user holding that right.

Once stopped, the released `ReadWriteOnce` claim can be mounted by a Job that runs that procedure.
  - **This operator has no supported stop yet** (#254, `spec.suspended`):
    - **Scaling the StatefulSet to zero is not a stop.** The reconciler writes `replicas: 1` on every pass.
    - **Deleting the `Agent` is not a stop either, and it destroys what the agent runs with.** The credential Secret is owned by the `Agent` and goes with it, both where the constructor builds it and where the issuer places it. A managed agent's lost key then meets a 409 rather than a second first certificate (`control.md`). The feed constructs a `Control`-source `Agent` again at once (above), so it does not even stay stopped.

- An agent's credential comes from `garam` on the route the claim admits this operator to, and is asked for only where what comes back can be stored at once. `garam` generates the private key per certificate and keeps none, so the store is what makes a credential obtained: nothing asks for one it already has somewhere to put, and a write that fails is answered by another certificate rather than by another write. A credential kept in this process to be retried is one only this process has.

The last two are different certificates and the wrong one fails at the handshake: an agent that pinned the issuer could not reach `garam` at all. `garam` answers when the certificate stops being valid, so nothing here parses a PEM to learn it.

An agent renews its own over the connection that credential authenticated, and this operator's route is what recovers one that expired — it answers again at any time, with no window and no lineage to lose, which is not how this operator's own identity behaves.

A claim reported against a definition is whichever assignment exists, so it survives a reassignment and says nothing about who holds the agent, and the epoch a definition's claim carries is therefore not the one this operator holds the agent at. This operator does not poll for its own dispossession: a credential already placed means no call is made, so it learns it was replaced the next time it needs one or the next time it reports, and it tears nothing down on either.
- An `Agent` the operator constructs is named for the digest of the whole agent GRN, and the Secret is named after the `Agent`. The name reads no part of the GRN — what its segments mean is `garam`'s — so nothing here moves if that format does. Both names are the operator's: the definition carries neither.

Force deletion does not wait for the kubelet, so a Pod that is gone is no evidence, and empty statuses or waiting states on a scheduled Pod are not either. So does a claim that is missing, differs from the UID the controller annotated on the Pod (`agent.garam.sh/pvc-uid`) when it first saw it running, or was created after the Pod. Without evidence, `WriterFence` is `Unknown` with the reason, the Pod is read again every 30 seconds, and no timeout releases it. Where the adapter is placed, a random token is minted into the Secret `<agent>-placement` before the first Pod, and again at each fence release before the next. The init container that copies the credential copies the token the same way, into a memory volume at mode 0600, and only the adapter mounts that copy. No adapter setting names the file yet, because garam#1169 has not published one. `status.placement` and `status.writerStopped` are reports that the controller never reads back.

It is claimed through the StatefulSet's claim template, a claim template's PVC carries no owner reference, and this operator sets no `persistentVolumeClaimRetentionPolicy`, so Kubernetes' `Retain` default holds and the cascade that removes the workload does not reach the volume. The claim is named for the StatefulSet, which is named for the `Agent`, and a constructed `Agent` for the digest of its GRN, so recreating the `Agent` for the same GRN rebinds the same volume. The workspace's claim is kept the same way.
- The epoch `garam` holds an agent at is recorded in `AgentStatus`, and copied into `spec.identity` beside it, and is written only where the certificate route proved it. That route answers for an agent assigned to this operator at the current epoch and refuses every other caller, so a certificate in hand is what makes the epoch beside it this operator's own rather than a number read off a list. It is never refreshed afterwards: a definition's claim reports the assignment's epoch whoever holds it by then, so an epoch re-read later would be current however long ago this operator was replaced, and a report carrying it could never be refused as stale — which is the whole of what the epoch is on a report for. An `Agent` a user wrote carries none, and neither does one constructed before this operator recorded them, because a claim is not repeatable and no route answers the epoch an operator holds an agent at.
- This operator tells `garam` what it sees of an agent's pod, and `garam` learns it here and from nowhere else: it dials no cluster and reads no pod. What it sends is read off the `Agent` — the epoch a construction recorded and the readiness a reconcile observed sit on one object — so nothing is handed between the two writers and one list answers every agent.
- Two of `garam`'s four provisioning states are reachable from what this operator observes, and the other two are named unreachable rather than approximated. A workload reporting a ready replica is `ready`; one reporting none is `provisioned`; a workload this operator did not read is not reported at all. `failed` needs telling a replica that cannot start from one that has not started yet, which needs container statuses a StatefulSet's status does not carry, so reporting it would assert more than was observed. `pending` is `garam`'s word for an agent no operator has reported on yet and is the value it already holds, so staying silent is how an operator leaves it standing and sending it would be a report asserting that no report has been made.
- What `garam` can conclude from `ready` is bounded by what a ready replica is worth, which is the same bound the `Available` condition carries: a replica is ready once its containers are running, this workload carries no readiness probe, and a container running the wrong binary is ready on those terms like any other. Issue #3's gap — a broken agent inside a running Pod is invisible from here — is carried one repository further out rather than closed, and the sentence saying so is written into the reported state's own documentation, where a caller of the route meets it.
- The report is sent on its own clock by a `Runnable` beside the poll and the renewal, and every pass reports every agent this operator holds a record of. `garam` keeps the last report and expires none, so a report skipped is one that never happens and no later pass corrects it; reporting unconditionally keeps the stored state equal to the last thing observed without this operator having to remember what it sent across a restart. It is not sent from a reconcile: the reconciler reads the `Agent` and nothing else, an unset address makes no outbound call because the whole `garam` side sits behind that one guard, and a call with a timeout does not belong on the reconcile path.
- A report `garam` refuses ends that agent's report and not the pass. A stale epoch and an agent this operator does not hold are different facts and neither is retryable — no route answers the epoch an operator holds an agent at — so both are reported and neither tears anything down, which is the answer this operator already gives for the same fact met at the certificate route.
- The poller and the reconciler both write an `Agent`'s status, and both write through a patch. The fields are disjoint — the poller reports the agent GRN, the reconciler the condition and the generation it was computed from — but the writes are not: an update carries the resource version the object was read at, so a report landing between a reconcile's read and its write is refused, and the reconcile fails on a race that resolves itself. A merge patch carries no resource version and names only the fields its writer decided, which is what makes disjoint fields disjoint writes. Measured on `garam-dev` on 2026-08-26, one report racing each of 40 reconciles: an update was refused 27 times and a patch none.
- An Agent reports two conditions, and they answer two questions. `Synced` says whether the cluster carries the workload the spec asks for, and the reason where it does not. `Available` says whether that workload reports a ready replica. `status.observedGeneration` says which generation both answers were computed from, so a status the controller has not caught up with is visible as one. A spec this controller cannot act on is reported on `Synced` rather than returned as an error, because an error would requeue forever and say nothing on the object.
- `Available` is read off the StatefulSet the reconciler already holds, and is reported on a spec this controller cannot act on as readily as on one it can. A workload whose volume size the spec can no longer ask for is still running, and a reconcile that reads the object anyway can say so for nothing; what it may not do is fetch something to answer, because a condition worth a second read is worth a watch instead.
- What this operator guarantees is still about the declaration. `Available` widens what is reported and not what is promised: a replica is ready once its containers are running, this workload carries no readiness probe, and a container running the wrong binary is ready on those terms like any other. Issue #3 records that a broken agent inside a running Pod is invisible from here, and this condition does not close that — the boundary is written into the condition's own message, which is where a reader of `kubectl describe` meets it rather than in a document they will not open.
- A reconcile that stops before reconciling a workload reports `Available` as `Unknown`, not `False`. It read no StatefulSet, and an Agent whose Secret was deleted after its workload was built still has that workload running, so `False` would be a claim about something this operator did not look at.

## Rationale

The layout and the generated manifests follow the scaffold, per [ADR 0001](adr/0001-kubebuilder-go-v4-scaffold.md): code is written to fit the CLI's paths rather than the CLI's output being reshaped to fit a preferred layout.

The workload's form is [ADR 0005](adr/0005-statefulset-of-one.md): a StatefulSet of one replica, because the agent's state is a single-writer store and the ordering guarantee is the only thing keeping two writers off one volume.

The image field was settled on issue #11, before the API was written, and carries no ADR: the rule is stated in the field's own doc comment, where it is enforced. "No outbound call in `v1alpha1`" was settled there too, as a milestone boundary rather than a project rule. ADR 0007 is where that boundary was crossed, and no field of the API moved when it was — which is what the boundary was drawn for.

The Pod's group and the group-readable mode are [ADR 0006](adr/0006-credential-group.md), settled on issue #31 after the e2e layer measured what no layer below it could see: a container that drops root cannot read an owner-only file the kubelet wrote as root. Its erratum of 2026-08-23 narrows what the group reaches, without moving the decision.

How a file its reader must own reaches that Pod is [ADR 0010](adr/0010-copy-an-agents-credential-into-a-memory-volume-the-pods-own-user-owns.md), settled on issue #82 once `garam` published the rule as a contract and refused the branch where the reader narrows it. It does not supersede ADR 0006 and nothing in ADR 0006 is false: that decision carries the projection into the Pod, and this one carries it from the projection to a reader that must own it. It is also where ADR 0006's rejected uid field is reopened and rejected again, for a second reason — the operator names the Pod's user instead of being told the image's. Its shape was measured on `garam-dev` under PodSecurity `restricted` before it was built, with two controls that separate the rule's two halves.

How the operator reaches `garam` is [ADR 0007](adr/0007-claim-definitions-from-a-poller.md), settled on issue #2 once `garam`'s own ADR-0033 decided the surface: a poll rather than a watch, a claim that binds the operator to the agent GRN a definition minted, and a second claim that is a conflict rather than an override. What it decides here is the division between what a definition says and what this operator builds, where the poll runs, what the operator authenticates as, what it verifies `garam` against, and where a claimed GRN is reported. Its Context listed five values keys as the ones `garam` expects; its erratum of 2026-09-27, from issue #155, records that the list was read off a schema example and `garam` publishes none. The division stands without it. That composition is `garam`'s, held as a definition's `values`, is superseded by ADR 0032; the rest of what it decides stands.

What rewrites the operator's own credential is [ADR 0008](adr/0008-renew-the-operator-credential-into-the-secret-it-is-read-from.md), settled on issues #74 and #76 once `garam`'s ADR-0046 gave an operator a route to renew over the connection it already holds. It closes ADR 0007's open question with a mechanism: one home for the credential, replaced through the API server rather than as a file, which is what lets a process that can write nothing on its own disk replace what it authenticates with. Its route was undeployed in `garam` when the decision was made and is deployed now, which the ADR records as two dated measurements rather than as a prediction.

How this operator gets a credential to renew at all is [ADR 0020](adr/0020-enroll-this-operator-with-a-one-time-token-and-keep-the-key-it-generated.md), settled on issue #126 once `garam`'s ADR-0064 gave a caller with no certificate one route it can reach. It extends ADR 0008 rather than superseding it: that decision put the credential in one home and left a person to place the first one, and this one makes the operator place it. What it decides is where the key is generated, what is checked before a token is spent, what verifies the call carrying it, what of the answer is kept, and why nothing retries. Its route was read at `garam@b16a896` and every enrollment in this repository's tests is served by a stub listener, because `admin@garam-dev` is read-only for this project.

What a refused token leaves behind is [ADR 0021](adr/0021-present-any-one-enrollment-token-once-and-wait-for-another.md), which supersedes ADR 0020 and carries every other decision in it forward unchanged. ADR 0020 bound one attempt to one process because a refused token was the end of the road; `garamsh/garam#1027`, closed on 2026-09-05, decides that a member may mint a second token for an operator holding no certificate and that the old one dies with it, so the person this operator waits on can now hand it another. ADR 0021 binds one attempt to one token instead and ends the `Runnable` on a certificate, which is what removes the Pod restart from the recovery. The minting route is decided and not built, which is why the refusal names no route.

Which certificate ends it is [ADR 0022](adr/0022-end-the-enrollment-on-a-certificate-that-has-not-expired.md), settled on issue #140, which supersedes ADR 0021 and carries every other decision in it forward unchanged. ADR 0020 wrote the guard as "no certificate this operator can read" and ADR 0021 repeated the words; the guard is `tls.LoadX509KeyPair`, which checks that a key matches a certificate and reads no validity, so an expired certificate ended the enrollment before the token file was reached. Both of this operator's recovery routes were then closed and each closed the other — a renewal must present the credential it is renewing. What ADR 0022 changes is the one word: the enrollment ends on a certificate that has not expired. It decides that expiry is read past `notAfter` on this operator's clock with no skew margin, that `notBefore` is not read, and that ADR 0020's guarantee against spending a token on a live credential is what bounds the narrowing rather than what it costs. The state it was measured against was live on `admin@garam-dev` on 2026-09-05; whether the enrollment it enables then succeeds rests on a lazy authority creation `garam`'s PM has read in source and never observed, because this guard is why nobody has reached that path.

Where the signal lands is [ADR 0030](adr/0030-carry-the-operators-certificate-expiry-and-garams-refusals-as-metrics.md), settled on issue #137 after the operator's credential ran out on 2026-09-04 while eleven hourly renewer failures sat among 2,147 poller errors in a log nobody read. It extends ADR 0008 rather than superseding it: nothing stops, and the metrics are a second place for the signal ADR 0008 kept. It also decides what ADR 0007 left open about metrics. The health probe was refused because a restart recovered nothing in either failure recorded there, and a local validity check because every one passed through the failure that happened.

What a claimed definition becomes is [ADR 0009](adr/0009-construct-a-claimed-agent-from-the-operators-own-configuration.md), settled on issues #75 and #79 together because neither can be built without the other's answer: an `Agent` needs an image, a storage size and a credential, and a definition carries none of the three. It decides where the first two come from, when the certificate route is called and what becomes of the answer, who names the objects, and where the epoch is met. Its route was measured on `garam-dev` before it was built, which is where the facts about the two roots, the unfenced re-issue and the unbranchable refusal come from.

That the image is maintained rather than only written is [ADR 0018](adr/0018-keep-the-image-of-an-agent-this-operator-constructed-current-with-its-own-configuration.md), settled on issue #121 after a corrected `--agent-image` was applied and repaired nothing. It extends ADR 0009 rather than superseding it: that decision put the image in this operator's configuration and made this operator the only writer of the field, and this one is what follows from being that writer. What it adds is which agents the correction reaches, what tells them apart, where it runs, and what it does not take with it. The distinction it rests on was measured on `admin@garam-dev` before it was built, and the cost of not having it was measured on the same cluster.

Where an agent's tool set is declared is [ADR 0012](adr/0012-declare-an-agents-tool-set-in-its-definitions-values.md), settled on issue #92. It extends ADR 0009 rather than superseding it: the sentence "no value of a definition names either, and none is read" decides the image and the storage size, and its reason — the audience a container choice asks — does not reach a value that chooses among the tools an image already carries. What it adds to the division is the other half of it: which values this operator carries, what becomes of the ones it does not, and how one reaches a Pod. It landed with no mechanism and nothing here reads a value yet, because both peer projects sequenced the declaration site ahead of the code that would carry it. Its declaration site, a `garam` definition's `values`, is superseded by ADR 0032, which moves the key family to the control store's desired definition; how a pin set reaches the Pod stands.

How the tool set an agent loads reaches its Pod is [ADR 0027](adr/0027-an-agents-tools-arrive-in-its-own-image-and-this-operator-mounts-no-tool-tree.md), settled on issue #173, which supersedes [ADR 0019](adr/0019-mount-an-agents-tool-tree-from-an-image-this-operator-names.md). ADR 0019 mounted a tree from an image this operator named because the agent image then shipped none; `sherlock` has since baked its tools into that image (`garamsh/sherlock#852`) and the tools image no longer exists, so ADR 0027 builds no tree and leaves the directory to the image. It answers issue #142's question whether a tools image exists. ADR 0012 stands under both: the directory is no definition's key, and what moved is only who writes it.

What renders a declared tool set into the Pod is [ADR 0024](adr/0024-write-an-agents-config-file-from-an-init-container-into-a-directory-this-operator-names.md), settled on issue #139, which is the one thing ADR 0012 named as left to its implementation issue. It extends ADR 0012 and supersedes nothing: that decision settled the key family, the closed set, the file and its mode, and this one settles what writes the file and where the agent finds it. Its ground is a measurement rather than a preference — a ConfigMap does not remove the container that has to write the file, because a Pod carrying a group cannot be handed an owner-only file by the kubelet — and the discovery road it takes is the one whose directory this operator can name. What it could not exercise is recorded with it: envtest has no kubelet and the e2e suite runs a substitute image, so the log line that says an agent runs unpinned has not been seen to stop.

What is supported is [ADR 0031](adr/0031-support-agents-declared-in-garam-on-one-cluster-of-the-sherlock-type.md), set by the owner on issue #202. It supersedes nothing: that agents are declared in `garam` is ADR 0007's division, the types on hold stay where ADR 0025 and ADR 0029 put them, and a hand-written `Agent` is still reconciled as `delivery.md` records. What it adds is which of the shapes those decisions allow is supported, why declaring `Agent`s in the cluster for `garam` to observe was not taken — it would move identity, per-agent certificates and single ownership out of `garam` — and what would reopen each point. Its §1, that agents are declared in `garam`, is superseded by ADR 0032; §2 to §4 stand.

Who owns an agent's desired definition is [ADR 0032](adr/0032-own-an-agents-desired-definition-in-this-projects-control-service.md), recorded on issue #205 from the separation of services the owner accepted on `garamsh/garam#1155`. It moves the definition, its templates and its revisions to this project's control service and leaves the GRN, authorization and collaboration with `garam`, superseding ADR 0007's composition, ADR 0012's declaration site and ADR 0031 §1 and nothing else. It keeps what ADR 0031 refused to give up: identity, the certificate route and the claim's epoch stay `garam`'s, and an `Agent` is rendered rather than a source. It decides ownership and invariants only; the control service is unbuilt and the wire contracts are agreed elsewhere, which is why the poller reading `garam` is recorded above as the present mechanism.

What carries an agent's model and ego is [ADR 0035](adr/0035-carry-an-agents-model-and-ego-in-its-spec-and-render-them-through-its-types-descriptor.md), settled on issue #151 once the PM narrowed it to `sherlock` and put the settings on `AgentSpec`. The separate `Model` kind the issue first asked for was not built: the desired source is to move to the control store (ADR 0032), and a kind here would be a second one. An agent this operator constructs is given neither field until then.

Where an agent's identity is carried is [ADR 0037](adr/0037-carry-an-agents-identity-in-its-spec-and-start-the-agent-under-it.md), settled on issue #219 once `sherlock@0ced773` made `--agent-id` required and `garam`'s adapter required the GRN. How the manager takes desired state from the control service, and how it keeps a GRN on one source, is [ADR 0043](adr/0043-pull-managed-agents-desired-state-from-the-control-service-and-keep-each-grn-on-one-source.md), the first slice of issue #217. It puts the consumer in a domain of its own, `internal/desired`, and moves the names the GRN derives below both sources into `internal/agentname`. It marks each `Agent`'s source when the `Agent` is built rather than reading status. It leaves garam#1171's import, freeze and switch of existing agents to later slices.

What holds an agent's next Pod off its volume until the last one's writers stopped, and what the adapter is given per placement, is [ADR 0042](adr/0042-fence-each-agent-pod-on-positive-evidence-its-writers-stopped-and-mint-an-adapter-only-placement-token.md), the first slice of issue #212. It supersedes this document's statement that the reconciler holds no finalizer: an `Agent` must outlive its Pod for the Pod's evidence to be persisted first. It keeps the claim's baseline on the Pod rather than in status, because the reconciler reads no status as an input. It states the one window a hand edit leaves: a claim recreated within the same second as the Pod's creation. Placement registration with the control service, leaf re-presentation, and the adapter's setting for the token wait on #218 and garam#1169.

Who gives an agent garam's reply instruction, and how, is [ADR 0041](adr/0041-join-garams-reply-instruction-to-the-ego-wherever-the-adapter-is-placed.md), settled on issue #236 once `garam` pinned the `garam-message.v1` envelope. The manager joins it to the ego wherever it places the adapter, because only it knows when an envelope arrives and because the ego a person edits should hold only their text. The control service adding it to every definition was refused on both grounds. That an agent with no declared ego loses `sherlock`'s default there is the price it records.

Where `garam`'s adapter runs is [ADR 0034](adr/0034-place-garams-adapter-as-a-native-sidecar-beside-every-agent-this-operator-constructed.md), settled on issue #216 once `garam`'s PM confirmed the split: `garam` owns the command and everything it does with a message, and this operator owns its placement. It follows ADR 0023's shape — an image the deployment names for a thing the workload carries, and an unset flag that builds the Pod built before — and ADR 0037 is what gives it the GRN it needs without reading a status. What it leaves unbuilt is recorded with it: the placement token (#212) and the outbox mount.

What that table carries is [ADR 0029](adr/0029-route-every-agent-specific-name-in-the-pod-through-its-types-descriptor.md), settled on issue #176, which extends ADR 0025: the two fields ADR 0025 named could not produce sherlock's variable names or its file, so the descriptor holds every name itself, and the Pod builder holds none.

It took ADR 0019's shape — a second image the deployment names for a thing the workload carries and no `Agent` names — which ADR 0027 has since retired for the tool tree and which stands for the workspace; it supersedes nothing: ADR 0005 keeps its single replica, and ADR 0010 is why the uid the workspace is told is 65532 rather than the 1001 its image would take. Where the workspace's files are kept is [ADR 0044](adr/0044-give-an-agents-state-and-its-workspace-separate-claims.md), settled on issue #249 after the gitops PM measured the workspace's exec uid reading and appending to the agent's memory store through the claim the two shared (gitops #288). Where the agent's memory store lives was settled on issue #157, and carries no ADR because it changes no rule: ADR 0005 already puts the agent's state on the claimed volume, ADR 0029 already routes every name the agent reads through the descriptor, and ADR 0023 already keeps the two processes to disjoint subtrees. What it corrected is a fact. Until then no agent this operator built wrote the volume: `sherlock`'s relative default put the store under `/home/nonroot`, and on 2026-09-06 the first agent constructed in production had nothing of its own on the volume. ADR 0005 carries an erratum saying so. Mounting the volume at `/data`, where the agent image's own comment points, was refused: the default resolves against `/home/nonroot` and not `/data`, so that mount would have stayed as empty. Nothing is migrated, because the production reading found nothing to move.

That the agent's state volume outlives the `Agent` was settled on issue #152 and carries no ADR because it changes no rule: it is what ADR 0005's claim template does once ADR 0009 names a constructed `Agent` for its GRN, and what is recorded is that the retention default is kept on purpose rather than left unset by omission.

Where the flags carrying all of this are set is [ADR 0013](adr/0013-the-base-carries-what-every-deployment-shares.md), settled on issue #105, and `configuration.md` is where it is described: the Secret and the four credential paths are the base's because the mount they read is, and the address, the agent image and the storage size are the deploying overlay's.

The condition this API reports was settled on issue #14, and carries no ADR for the same kind of reason: its type and its reasons are constants in `api/v1alpha1`, and the field's own doc comment names them where a user of the API reads them.

The second condition was settled on issue #103 and carries no ADR either. What it reports was decided in issue #3 clause 5, that CR status carries Pod state, and this is that clause implemented rather than a decision taken here; what is chosen is the name, and Kubernetes chose it first — a Deployment splits the same question into `Progressing` and `Available`, and this operator's `Synced` already holds the first half. `Ready` was the other candidate and is a Pod's word for its own containers, which on an `Agent` would read as a claim about the agent. The reasons and the sentence bounding what a ready replica is worth are constants and a message in `api/v1alpha1`, which is where issue #14 put the first condition's.

What the workload's security context carries was settled on issue #85 and carries no ADR: `restricted` is a published standard rather than a choice this project makes, and the four fields it asks for were left undecided by ADR 0006 on a ground — that each constrains what a user's image may be — which holds for one of them and not for the four. That one is left open below.

What is settled beside it — that `spec.image` accepts a tag — moves no rule either. The field accepted one before, and what accepting one costs is stated in the field's own doc comment, which is where issue #11 put the field's rule.

What this operator tells `garam` about an agent's pod is [ADR 0016](adr/0016-report-what-the-operator-observed-and-stay-silent-where-it-observed-nothing.md), settled on issue #117 once `garam` published a route for it. It decides four things that depend on each other in that order: where the epoch lives between the claim and the report, which of `garam`'s four states this operator can honestly reach, when a report is sent, and what a refusal does. It closes the open question ADR 0007 left about what this operator reports back, for the provisioning half of it. Its route was read at `garam@e1e69fd` and every report in this repository's tests is served by a stub listener, because `admin@garam-dev` is read-only for this project.

That both writers of an `Agent`'s status patch was settled on issue #84, and carries no ADR because it changes no division: the poller reported the GRN before it and reports it now. What moved is the reconciler's write. ## Open questions

- **What rewrites the file `garam`'s listener is verified against.** ADR 0008 replaces the certificate this operator presents and leaves this one alone: a renewal answers with the `garam` server root beside the credential, and taking it would make the operator rewrite what it verifies `garam` by out of an answer that root was used to verify. ADR 0020 meets the same field in an enrollment's answer and leaves it alone for the same reason, so the question now stands over two answers rather than one. What the deployment supplies stays the deployment's until something decides otherwise.
- **What else this operator reports back to `garam`.** ADR 0016 answers the provisioning half and leaves two. Runtime state is the agent's own account of itself and is reported on a route this operator is refused, so it is not this operator's to send and no agent image exists to send it. ADR 0012 gives the question a second subject that no route touches: a value this operator ignored is reported in this operator's log and a pin an agent cannot satisfy in the agent's, and neither log is one a definition's author reads.
- **Whether `failed` should become reachable.** It is the state `garam` most wants and the one this operator cannot earn from a replica count. Reaching it means reading Pods, which issue #72's ruling makes a watch rather than a second read, and it would move the `Available` condition and the sentence bounding it as much as the report — telling a replica that cannot start from one that has not started yet is a change to what this operator observes, not to what it says. What would settle it is a deployment that has to act on the difference; `garam` publishes nothing an operator should do about `failed`, which is the same gap this document records for a reassignment.
- **When a tool set edited after construction reaches the agent.** ADR 0032 decides that the manager owns every field of an `Agent` carrying a GRN, which answers whether a tool set edited after construction should reach the agent: it should. Until that is built, a declaration is written into the `Agent` once and a pin set changed in `garam`'s console afterwards reaches nothing, as `spec.image` did before ADR 0018. What settles it is the change that moves the manager onto the control store.
- **Whether a model's key can be kept from the tools an agent spawns.** ADR 0035 places it in the agent's environment because `sherlock` reads it from nowhere else, and `sherlock` hands that environment to every tool. Narrowing it is `sherlock`'s change — a key read from a file, or a runner that strips the variable — and what would settle it is `sherlock` offering either.
- **How the adapter reaches the agent's outbox.** `sherlock` writes it to `/var/lib/sherlock/memory/outbox` on the state volume (`sherlock@ecf4621:internal/gateway/outbox.go:18-26`), and the adapter owns reclaiming it, so it would need to write there; at `garam@fdfb76d` no adapter setting names an outbox, and that side of garam#1169 is unbuilt. ADR 0034 mounts nothing for it. Who owns the mounted directory is part of the answer: a `subPath` the kubelet creates before `sherlock` does is root-owned and `sherlock` could not write it. What settles it is the adapter setting that names the outbox, which adds the mount with it. That mount is the `state` claim, into the adapter alone: the workspace never mounts it (ADR 0044).
- **Whether an agent's required tool set should be reachable from configuration at all.** Nobody has answered it. `sherlock` holds the invariant deliberately, which is why the required set exists, and has not decided that reaching it from no configuration is right; this operator has no basis to decide that for them, and reads no key for something it could not deliver. What would settle it is an agent whose author needs to see or change the required set, rather than an operator asking for the switch on principle.
- **Whether an agent renews into a copy nothing refreshes.** ADR 0010 delivers the credential as a copy made once at pod start, which is the shape `garam`'s own chart renders and carries the same limitation. `garam`'s contract expects whatever refreshes such a copy to satisfy the arrival rule on every refresh, and nothing in this Pod refreshes it; the agent's mount is left writable so that the agent itself can. What would settle it is a measurement of what the adapter does with the file when it renews.
- **What else runs beside the agent in the Pod this operator builds.** Half of this is answered: `sherlock`'s workspace is a second container and this operator builds it, per ADR 0023. The other half is not. `garam`'s adapter is the third, and this operator builds it, per ADR 0034. What an agent image is expected to already contain, beyond running as the user the Pod names, is still not stated anywhere this repository can point at.
- **What an operator does when it learns it no longer holds an agent it is running.** The refusal reaches this operator only when it next needs a credential, and it acts on nothing: the credential in the Pod is the agent's to renew and `garam` publishes nothing that says an operator should stop. Whether the workload should be torn down, reported on, or left is undecided, and what would settle it is a reassignment happening to a running agent rather than to a test row.
- **Whether an agent's credential is ever replaced from this side.** An agent renews its own and this operator's route recovers one that expired, so the remedy exists and is unfenced. What is unmeasured here is whether the agent renews at all in practice and what it does when the file changes under it — its behaviour rather than this operator's.
- **No image here refuses a mode `garam` would.** The e2e suite runs a substitute image, and a substitute brings its own acceptance rules. The suite now applies `garam`'s rule to the delivered file itself, with a control the rule refuses, so the layer says whether the file would be accepted; what it still does not say is whether a `garam` process reads it, which needs an image that applies the rule at startup. `Available` reports green over that same substitute rather than over an agent — a stand-in the suite builds from `test/e2e/agent-image/`, which accepts the command line this operator gives `sherlock` and refuses one with no agent ID — so it adds a layer that reads green and not an execution, and what would settle it is the same missing image.
- **Whether the agent's uid can execute the tools it is given.** The tools arrive in the agent's image, owned by uid 65532 (`sherlock@35e79b5:build/agent.Dockerfile:70-74`), and the Pod runs as that uid, but no layer in this repository executes one: the integration layer has no kubelet and the e2e suite runs a substitute image. What would settle it is a bring-up of a published agent image.
- **Whether an agent's workspace can isolate an exec on the nodes this operator builds for.** The unprivileged path `sherlock` takes at a non-root user clones a user namespace, which needs unprivileged user namespaces enabled on the node — `sherlock` refuses the call where they are not — and which the seccomp profile this Pod names may or may not permit; nothing in this repository can answer either, because envtest has no kubelet and the e2e suite runs a substitute image. Both bound the isolated subset only: a call that does not ask for network isolation reaches neither, and both present as a refused exec rather than as a Pod that fails to start. What would settle it is one exec, asking for isolation, on a node of the deployment's own.
- **Whether an agent's image may write its own root filesystem.** `readOnlyRootFilesystem` is the part of the Pod's security context ADR 0006 left undecided that issue #85 did not settle with the rest. It is no part of PodSecurity `restricted`, so nothing refuses the workload without it; the manager sets it on itself and this operator sets it on none of the containers it builds, because the field constrains what an image needs rather than what it is allowed to do and no image in the Pod is this operator's — the agent's is the deployer's or the user's, and the copy tool's is the deployer's, asked for a shell, `install` and `mkdir`, and nothing more. Setting it on the init containers alone would buy a guarantee about filesystems discarded when those containers exit, at the price of another clause on `--agent-copy-image`. What would settle it is a deployment that has to refuse an agent image the right to write its own filesystem.
- **What a corrected image costs an agent that is running.** Bringing `spec.image` current rolls the StatefulSet's replica, so an agent holding a session loses it without being asked. Nothing drains it first: this operator reads a replica count and no readiness probe, and `garam` publishes no route that asks an agent whether it may be replaced — the same gap issue #3 records one layer out. ADR 0018 accepts that price against an agent that otherwise never runs at all, and answers nothing about an agent that is working. What would settle it is a route that says whether an agent is busy, or a deployment that has to correct an image without interrupting one.
- **What grace period an agent's Pod needs.** `sherlock@2ad4c13` drains on SIGTERM by committing the current turn and releasing its writer lock last, and the kubelet's SIGKILL at the end of `terminationGracePeriodSeconds` cuts a longer drain short. The Pod sets none, so the 30-second default applies. What would settle it is a measured turn-commit time stated as the value.
- **Resizing an agent's volume.** A StatefulSet's claim template is immutable after creation, so a change to `spec.storageSize` on an existing `Agent` cannot be satisfied by editing the workload. ADR 0005 accepts the limitation without answering it. The controller leaves the claim as it is and says so on the object, which makes the limitation visible without answering it either.
- **Who reclaims the volume of an agent GRN that no longer exists.** The volume is kept so that a reconstruct can rebind it, and nothing here can tell a volume no reconstruct will ever rebind from one that one will: this operator deletes nothing but the StatefulSet of a deleting `Agent` (ADR 0042), whose claim template's claims the deletion does not reach, and learns of no agent's end. A GRN does not come back once its definition is gone, so such a volume accrues once per agent that ends; issue #152 records three on the `gitops` cluster on 2026-09-06, none bound and none owned. What would settle it is a route that says a definition is gone, or a deployer who has to reclaim one.
- **What `workspace` means as a value key, if it is ever one.** The word names three things: a project GRN in `garam`'s `AgentValues` example (`garam@8f9dd9d:api/openapi.yaml:1606`); the place an agent's actions run and its capabilities are enforced, in `garam`'s ADR-0012 (`garam@8f9dd9d:docs/architecture/adr/0012-agent-operator-model.md:31,67`) and in the second container ADR 0023 builds here; and, in ADR 0007, a composition value `garam` would hand this operator. Nothing reads a key of that name. Nothing here settles which, if any, a definition's `workspace` key would mean; what would is a key this operator is asked to read, with `garam` stating what its value names.
