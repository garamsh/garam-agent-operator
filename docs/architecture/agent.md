# Agent

The `agent.garam.sh` API group, the `Agent` kind it serves, and the controller that reconciles it.

## Current decisions

- `Agent` is served at `agent.garam.sh/v1alpha1` and is namespaced. Its types live in `api/v1alpha1/` and its reconciler in `internal/controller/` — the paths the kubebuilder CLI owns.
- An agent's desired definition — what it runs with, the templates it is made from, and the revisions of both — is owned by this project's control service, whose store is the one place it is written. `garam` owns the agent's stable identity, its GRN, together with organization authorization and collaboration, and the manager renders each `Agent` from the control store. An `Agent` carrying `spec.identity` is the control service's: the manager builds one only from the control service's desired feed, and nothing else builds one ([ADR 0077](adr/0077-build-agents-only-from-the-control-services-feed-and-remove-the-legacy-path-and-the-cut-over.md)). A manager with no `--control-address` builds no agents, whatever else it is given.
- For every `Agent` carrying `spec.identity` the manager renders the spec from the control service's feed on every new revision: model, ego, tools, the profile's resources, storage size, storage class and workspace size, the assignment epoch, the revision itself as `spec.revision`, and the operator's image. A hand edit to one of those is reverted at the next revision. The puller renders every agent again after a restart, so a changed `--agent-image` reaches every agent then. An `Agent` with no GRN is not rendered from anything.
- The manager pulls the feed (`internal/desired`) only where `--control-address` is set, presenting a `garam` token minted for the control service, whose GRN `--control-grn` names, and its own GRN in `Controller-Grn` (ADR 0072). It verifies the control service against `--control-trust-file`. It holds the cursor in memory and renders only a revision it has not already rendered.
  - **Status.** It reports each rendered revision as observed and rendered.
  - **Transient errors.** A 500, a 503 or no answer is asked again after a wait doubling from 1 to 30 seconds.
  - **Refusals.** Any 4xx, including 422 `too_many_agents`, is asked again only every 5 minutes. It is counted in `garam_operator_control_refusals_total{route,status}` and shown in `garam_operator_control_feed_refused`.
  - **Withheld agents.** An agent the feed stops naming keeps its `Agent`: rendering deletes nothing.
- A GRN the feed names with no `Agent` is a managed agent. Its `Agent` is created by the feed, with `spec.identity` and the names the GRN derives, and it waits as `CredentialsSecretMissing` until the refresher places its first tokens, as below. The renderer refuses an `Agent` under that name that carries no identity or another GRN, `ErrNotControlSource`: a person wrote it, and it is left as it is.
- A model's embeddings endpoint arrives on the feed as `configuration.model.embedding` `{baseUrl, name, apiKeyRef}` (ADR 0052), and a model other than `mock` without one, or an embedding missing its base URL or name, leaves that revision unrendered as malformed. A model's key reference from the feed is `<secret-name>/<key>` in the `Agent`'s namespace, the name a DNS subdomain and the key `[-._a-zA-Z0-9]+` and neither `.` nor `..`, as Kubernetes requires of a Secret's name and data key (`k8s.io/apimachinery@v0.36.0` `pkg/util/validation` `IsDNS1123Subdomain`, `IsConfigMapKey`). A malformed one leaves that revision unrendered and unreported. The control service refuses the same references before storing one (its `definition.SecretRef`). The rule is stated once, in `internal/secretref`, a package below both binaries that the renderer and `definition.SecretRef` both parse with (#248).
- Every `Agent` carrying `spec.identity` has its `garam` tokens minted and kept current by the refresher (`internal/garam`, a `Runnable` beside the puller, only where `--control-address` is set), at `--garam-address` with `mintAgentToken` under this operator's own token (garam `afde8b8` `api/machine.yaml`; [ADR 0073](adr/0073-give-every-agent-garam-tokens-its-assignee-mints-in-place-of-a-certificate.md)). No certificate is issued, copied or recovered for an agent.
  - **What it mints.** For every such agent, a token with no audience, which `garam` accepts, and a second with the control service, `--control-grn`, as its audience, which its fenced adapter presents. Each is minted afresh under this operator's token: no agent token is exchanged for its successor.
  - **Where it writes them.** The agent's credential Secret, `<agent>-credentials`, owned by the `Agent`: `token`, `control-token` and the `server-root.pem` the mint answered, with the refresh time as `agent.garam.sh/tokens-refresh-at`, in one write. It creates the Secret where none is placed. It reads the Secret's metadata alone, from the cache.
  - **Under the version it read.** A write names the Secret's resource version as the refresher read it, so a recovery recorded in between refuses it and the next pass mints in the new lineage.
  - **When.** Every 10 seconds it reads which agents are due. A refresh is due at a random point from two thirds to three quarters of the time from the mint to the earlier token's expiry (garam ADR-0100). That leaves at least a quarter, 15 minutes at the one-hour default, for the kubelet to swap the Secret into the adapter's volume, which takes about a minute. A Secret with no refresh time is due at once.
  - **Refused.** A 403, an agent `garam` does not hold at the current epoch, is reported by name as `ErrAgentNotHeld`. A token minted at another epoch than `spec.identity.assignmentEpoch` is not written and is reported as `ErrMintEpochSuperseded`. So is one whose `spec.identity.assignmentEpoch` is not an integer, as `ErrEpochUnreadable`. A failure that belongs to one agent, that one or a failed read of its Secret, is that agent's alone: it is reported naming the agent, and every other agent is still refreshed. Each waits 5 minutes before it is asked about again, never a refresh's 10 seconds. Any other failure waits 30 seconds, and the next attempt writes the tokens the failed one minted rather than minting again, because `garam` keeps an agent's newest five per audience; a change to the Secret's version since, a recovery among them, discards them. Refusals are counted in `garam_operator_refusals_total{runnable="refresher",kind}`.
- A managed agent's credential recovery is prepared, and its new lineage recorded, by the recoverer (`internal/desired`, a `Runnable` beside the puller, only where `--control-address` is set) (#300, [ADR 0073](adr/0073-give-every-agent-garam-tokens-its-assignee-mints-in-place-of-a-certificate.md)).
  - **What it takes.** Each agent the feed names with an open `recovery` (the puller offers every answer's set whole), and each agent with a recovery request persisted.
  - **Persisted first.** It persists the recovery's request id and epoch in `<agent>-recovery-request`, owned by the `Agent` and mounted nowhere, before sending them as `{requestId, epoch}` to `POST /v1/operators/self/agents/{grn}/recovery-requests`. A restart sends the persisted request, and a persisted request is finished before another is begun. A recovery whose lineage was recorded is not begun again while the feed still names it, before its next answer.
  - **Prepared, then finalized.** Control answers 202 until an administrator finalizes, and the recoverer asks again every 10 seconds. A 200 carries `garam`'s new `lineage`.
  - **Recorded.** One merge patch writes the annotation `agent.garam.sh/credential-lineage` on the credential Secret and removes its refresh time, so the refresher mints the agent's tokens in the new lineage on its next pass. The request Secret is deleted after it. An agent with no credential placed has nothing to record: its first tokens are minted in the new lineage.
  - **The Pod moves.** The reconciler carries that lineage on the Pod template, so a recovery rolls the Pod through the writer fence. `garam` refuses the same generation after a recovery, and the next placement activates under the new lineage's token. An agent never recovered carries no lineage and changes no template.
  - **Status.** On an `Agent` carrying `spec.identity`, `Recovery` is `True` (`Recovering`) while a request is persisted, and `False` (`NotRecovering`) otherwise. The reconciler writes it from the request Secret's metadata.
- The `Agent`, its StatefulSet and its volume claim are named for the digest of the GRN, so an `Agent` created again for the same GRN rebinds the same volume. No new GRN is minted for an agent that has one, and the assignment epoch stays `garam`'s.
- Every connection leaves the cluster this operator runs in. No broker stands between the manager and the control service, and `garam` relays nothing between them.
- The supported scope is agents with an identity in `garam`, on one cluster, of the `sherlock` type. One cluster running one operator is what is supported, though nothing here prevents a second; `claude-code` and `codex` are on hold, admitted and refused as below. A hand-written `Agent` is for development and bring-up only: it is reconciled, but it has no GRN and no token `garam` minted for it, so `garam` does not see it. The scope is stated, not enforced — nothing refuses what lies outside it.
- `AgentSpec.Type` names the agent binary the workload carries. It is optional, defaults to `sherlock`, and is validated at admission against the closed set `{sherlock, claude-code, codex}`. An unknown type is refused at admission by the kubebuilder validation; an admitted type that this controller version has not yet learned to build is refused on reconcile with `Synced=False, Reason=TypeUnimplemented`. The kind itself is unchanged — `Agent` is the generic name, and the type decides every name the Pod builder writes that is the agent binary's. Adding a new agent binary is a code change, with a new entry in the controller's per-type table; it is not a configuration change.
- The type's descriptor carries every such name, and the Pod builder reads them from it: the credential's mount path, the state volume's mount path, the memory store's path under it and the variable the agent reads it from, the configuration directory, the variable the agent reads it from, and the config file's path under it, the text the file renders to, the variable the model's key is placed in, the ego file's path, the agent's command line, the workspace's address and its four variables, and the gateway's address `garam`'s adapter dials. For `sherlock` each is cited to `sherlock@8218189:docs/architecture/deployment.md` at the field that holds it. Every field is required, and a type whose descriptor leaves one unset is refused with `TypeUnimplemented`, as `claude-code` and `codex` are. What every type shares stays out of it: container and volume names, the Pod's user, group and security context, the credential's modes, pull-always, and the owner-only mask.
- `AgentSpec` carries what an agent needs to run: the container image, the Secret its credential material comes from, the persistent volume it keeps state on, the compute resources its container asks for, and optionally its tool set, its model, its ego and its identity. `AgentStatus` carries observed state only, and nothing a user writes.
- The agent's memory store is on the volume its state is claimed on. This operator writes its path into the agent's environment on every Pod, absolute and one directory below the volume's mount; for `sherlock` the variable is `SHERLOCK_MEMORY_PATH` and the file `memory/memory.db`. `sherlock`'s default is relative and resolves against its image's working directory, on the container's own filesystem, so an agent left to it keeps its store in the Pod and loses it with the Pod. The store has a directory of its own because `sherlock` derives its outbox beside it: the two share one subtree of the volume, disjoint from the workspace's.
- The image reference is required and has no default. No registry or tag convention exists for the agent image and neither project owns one, so the field asks rather than invents; a default can be added later to a field that already exists. Who it asks is the operator's deployer and not the agent's author: an agent's definition says what the agent is, and what container that is built from is this operator's to decide.
- Every container of an agent's Pod pulls its image at every start. `sherlock` requires a consumer of its images to reference a digest and pull always (`sherlock@04ed05a:docs/architecture/adr/0020-immutable-image-repositories.md`), and this operator is that consumer: the repositories holding `sherlock`'s bring-up builds are emptied once a release path publishes, and the orchestrator's default leaves what that breaks as a stale cache on whichever nodes hold one, presenting as those nodes' fault rather than as one refusal every replica meets. The init container's image is not `sherlock`'s and that record does not reach it; it is pulled the same way on a ground of this operator's own — the image comes from this operator's configuration and nothing here requires its tag to name one build, so a node's cache would leave two agents' credentials copied by different tools under one name. What it costs is that an image no registry serves cannot be run, whatever put it on the node.
- `spec.image` accepts a tag and says what the holder of one is accepting, rather than requiring the digest half of that obligation. The field names any image and this operator owns no registry the requirement could rest on, so a refusal would fall on references `sherlock`'s record says nothing about — the image a rendered agent is given among them, which arrives from a flag no schema reaches and would be refused when the renderer created the `Agent` rather than when the operator started. What a tag costs is stated where its holder reads it: pulling at every start makes a moved or emptied tag a restart that runs different bytes, the same on every node rather than a difference between them.
- Credential material is referenced, never carried. An `Agent` names the Secret, and the workload mounts its keys as files — the credential does not travel through environment variables. A model's API key is the one key that does, because its reader accepts nothing else; see below.
- The Pod carries a supplementary group, and the Secret is projected readable by that group rather than by its owner alone. A Secret volume's files are owned by root, so an owner-only mode leaves them unreadable to a container that drops root — and the operator cannot know which uid an arbitrary image runs as. A group needs no such knowledge: the kubelet puts every volume of the Pod under it and hands it to each container's initial process, whatever user that container runs as. It reaches no further on its own — a descendant that drops its supplementary groups leaves the group behind, and the credential with it. The same group is what makes a freshly provisioned state volume writable where the provisioner does not hand it over. Measured on 2026-08-24, on a volume a `csi.proxmox.sinextra.dev` StorageClass provisioned: the mounted directory is owned by root at mode 2775 with the Pod's group, and the container's own uid, which is neither root nor that gid, writes to it.
- The adapter alone mounts the credential Secret's projection, read-only at `/run/garam/credentials`: the agent's `garam` tokens and the `garam` server root ([ADR 0073](adr/0073-give-every-agent-garam-tokens-its-assignee-mints-in-place-of-a-certificate.md)). `garam`'s token-mode adapter reads each token file before every call and never caches it, and the kubelet swaps a Secret volume's files by rename, so a token the refresher replaces is read on the adapter's next call with no restart (`garam@afde8b8:docs/architecture/adapter.md` §Token mode).
- What confines a token is which containers mount the volume, not the file's mode. The adapter does not check a token file's mode (the same section), and the Pod names one user that every container runs as, so an owner-only copy would exclude none of the Pod's containers. Only the adapter mounts the tokens. The agent container mounts `server-root.pem` alone, out of the same Secret, at the descriptor's credential path, and only where it is given `garam`'s issuer (below). The workspace mounts nothing of it.
- The Pod names one user and every container runs as it. The operator names that user rather than being told it: an owner is one value for a whole Pod, and a uid taken off any one image stops being that value as soon as a second image in the Pod reads the same file. What an agent's image owes in exchange is stated on `spec.image`, where a user of the API reads it.
- The image the init containers run is this operator's own configuration and is required of every deployment. It needs a shell, `install` and `mkdir`, and nothing of the agent; the agent's own image cannot stand in, `sherlock`'s being distroless (`sherlock@e9c12a5:build/agent.Dockerfile`).
- What that gives up: an agent image that cannot run as the user the Pod names cannot be run at all, where a group asked nothing of the image.
- The workload is a StatefulSet of one replica, or of none while the `Agent` is suspended or its memory moves, with a volume claim template for the agent's volume. Once a move put its memory on another claim, that claim is mounted by name instead (ADR 0065).
- The workload is one a namespace enforcing PodSecurity `restricted` admits. The Pod asserts `runAsNonRoot` beside the user ADR 0010 named — naming a user the standard would accept is not the same as asserting one — and names the runtime's default seccomp profile; each container drops every capability and the right to gain a privilege. Those are the four the standard asks for and the four it refuses a Pod without, and none takes anything from a workload of this shape: the init containers run `install` and write a file, the agent runs whatever it runs, and the workspace executes its children through a path that asks for no capability at a non-root user. What they ask of an agent's image is stated on `spec.image`, and no flag offers any of them — the audience for one is the deployer already told the image must run as uid 65532. Measured on `garam-dev` on 2026-08-26, in a namespace labelled `pod-security.kubernetes.io/enforce=restricted`: the workload this operator builds was admitted and its Pod ran, with the credential arriving at mode 600 owned by the uid that read it; the same workload without those four fields had its Pod refused on all four, so what is admitting it is the security context and not the namespace.
- `readOnlyRootFilesystem` is set on none of the Pod's containers. It is no part of `restricted`, so nothing refuses the workload without it, and it is the one field of the Pod's security context this operator has not decided.
- An Agent's name is bounded at 52 characters, and the API server is what refuses a longer one. The workload's Pods carry that name with a suffix in a label — the longest is the revision hash, up to 11 characters — and a label value stops at 63. A name the API server took and the workload could not use would leave the controller building a StatefulSet whose Pods the API server then refuses, with nothing to retry.
- An Agent whose credentials Secret is absent gets no workload at all, and the Secret's arrival is what builds it. The Secret a model's key comes from is waited for the same way, reported as `ModelKeySecretMissing`, since a variable taken from a Secret that does not exist leaves the container unable to start just as a missing volume does. Mounting a Secret that does not exist leaves the Pod unable to start, and creating that Secret is not an edit to the Agent, so the controller watches the Secret rather than waiting to be woken by a spec change.
- No field of `v1alpha1` names an external system. What the operator needs to reach `garam` is process configuration — the machine listener's address, the three files of the key `garam` issued it (the private key, the `client_id` and the `tokenUrl`), and the file the listener is verified against — and an unset `--control-address` leaves it making no outbound call at all.
- The operator authenticates to `garam` with a token it exchanges under its own private key, as `private_key_jwt` under `machine-token.v2` ([ADR 0072](adr/0072-authenticate-the-manager-and-the-control-service-to-garam-with-their-own-private-keys.md)). `internal/machinetoken` signs each assertion with `go-jose` v4:
  - the key file is read again at each exchange, and `kid` is the RFC 7638 thumbprint of the key that signs;
  - the protected header is `alg` RS256, `kid` and `typ` JWT, and nothing else;
  - `iss` and `sub` are the `client_id`, and `aud` is the `tokenUrl` as one string;
  - it lives 60 seconds, and its `jti` is 256 random bits, never sent twice.

  It is sent to `/oauth/token` on `--garam-address`, which need not be the `tokenUrl`'s host.
- The token is presented as `Authorization: Bearer` and replaced once two thirds of its lifetime have passed.
  - A 401 from a call re-exchanges once, with a new assertion.
  - A 429 waits its `Retry-After`. Any other failure waits from 1 second, doubling to 5 minutes.
  - The token held goes on being presented while it lives, so a failed exchange stops nothing.
  - `invalid_client` is reported by that name, and nothing else is tried in its place.
- The key lives in one place: a Secret a person places from `garam`'s key issuance, mounted read-only into the manager's Pod.
  - The Pod carries the supplementary group the agent's workload does, and the volume is mounted group-readable, because the kubelet writes those files as root whatever user the container runs as.
  - This operator writes nothing to the Secret and holds no RBAC on it. A key is rotated by placing another, which the next exchange signs with; a lost one is issued anew by a person.
  - No key, assertion or token reaches a log line, a metric, an event or an error.
- Failed exchanges and `garam`'s refusals are carried as metrics as well as log lines, on the endpoint the manager already serves and through the registry controller-runtime owns. The names and labels are a stable surface an alert is written against, and they are the signal for a deployment that scrapes:
  - `garam_operator_token_exchange_failures_total{audience, reason}` counts each failed exchange. `audience` is `garam` or `control`, and `reason` is `key`, `invalid_client`, `throttled`, `refused` or `unavailable`. Because a failed exchange stops nothing, it rises while calls still succeed on the token held, which is the notice ahead of every call failing.
  - `garam_operator_refusals_total{runnable, kind}` counts every refusal `garam` answered a call. `runnable` is `refresher`, and `kind` is the HTTP status it answered.
- A sustained loss of authentication shows in readiness, for a deployment that scrapes nothing ([ADR 0075](adr/0075-hold-the-manager-and-the-control-service-not-ready-while-their-garam-authentication-has-failed-for-an-hour.md)).
  - **The checks.** Each token source adds a readyz check: `garam-authentication`, and `control-authentication` where `--control-address` is set. A check fails while every exchange and every call under that source has failed for longer than one hour, `machinetoken.SustainedFailure`, which is one lifetime of the token `garam` answers.
  - **What counts.** A failed exchange opens a run, and the next exchange that answers a token ends it. A call still answered 401 after its re-exchange opens a run that only a call answered below 500 and not 401 ends, because that re-exchange answers a token whether or not `garam` accepts it. A 5xx and no answer count as neither.
  - **Keeping the token.** The leader asks each source for a token every 30 seconds, so a source exchanges on its own schedule whatever else calls it. The `garam` source also calls `garam`'s `getIdentity` under its token at start and every 5 minutes, so a refused token meets a call's outcome with no other traffic. A run on the `control` source is ended by the next call the control service accepts, which the desired-state puller sends at least every 5 minutes. A replica that is not the leader calls nothing and stays ready.
  - **What not ready does.** The manager keeps its Lease and runs on, serves no webhook, and leaves only the metrics Service's ready endpoints. `/healthz` stays a ping, so nothing restarts.
- What is counted as a refusal is `garam` refusing and not this operator failing: a listener it did not verify or did not reach, and an answer it could not decode, are not counted.
- The key volume is optional, so a deployment given no identity still starts. Until the Secret is placed, every exchange fails with `reason` `key`.
- What the listener is verified against is a file the deployment supplies, `--garam-trust-file`. It holds whatever `garam` presents, and what that is has already moved once: the leaf `garam-dev` served until 2026-08-26, and since then a `garam` machine server root that signs it and is a separate certificate. The flag is named for its role so that only the file's contents move, which is what happened. Verification is never skipped, under a flag or otherwise.
- A desired definition says what the agent is and this operator says how an agent is built. What the agent is belongs to the control service's store, and the storage sizes are its profile's. The image is this operator's: `AgentSpec` keeps `image` required and `--agent-image` supplies it, because no field of a desired definition a member edits names one. A console user choosing an agent's container would be choosing what this operator runs as a root-capable workload in a cluster they cannot see, and `v1alpha1` carries no override for one.
- The directory an agent loads its tools from is declared in no desired definition, and this operator does not write it either. The agent's image carries its first-party tools and sets `SHERLOCK_TOOLS_DIR` to where they are (`sherlock@35e79b5:build/agent.Dockerfile:74-77`), so the directory is the image's and a variable written here would only override it. A definition naming it would point the agent at a directory whose contents its author controls, which is why no definition declares it. The container's `command` is left unset as it always was, so the image's entrypoint is what runs; its `args` carry the agent's identity and, where declared, its ego, as below.
- Which tools an agent has follows from the build `--agent-image` names, and this operator builds no tool tree into the Pod: no image volume, no mount and no variable. A cluster changes its agents' tool set by naming another build. A workload an operator that still named a tools image built loses the tree on the next reconcile, because the Pod's volumes, the agent's mounts and its environment are written whole on every pass.
- The process an agent's files and commands are served by is a second container of the same Pod, running an image this operator's configuration names. `sherlock` splits the two deliberately: the agent's image is distroless and carries no shell, and an Exec child is `sh -c`, so running the workspace out of the agent's image fails at the first call. The agent executes nothing itself and reaches that process over the Pod's loopback interface.
- Both ends of that link are written by this operator rather than left to the two images' defaults. The workspace is told where to listen and the agent is told the same place to dial, at a loopback address — the only bind `sherlock`'s listener accepts while it carries no authentication. The two images already default to the same number, so nothing changes today; what changes is that the agreement is this operator's, where two defaults agreeing is not one number chosen and neither image moving its own would be noticed here.
- The workspace is told to run exec children as the user the Pod names. `sherlock` runs a child under its own account only where that number matches the uid it already has and refuses every isolated exec otherwise, and the two are made equal in that direction because the Pod's user is a number this operator chose with a recorded reason while the image's is one the image chose. No container names a user of its own.
  - **It is `sherlock`'s supported unprivileged shape** as of `sherlock@26418f6` (#1052, `docs/architecture/deployment.md:91` there): the workspace runs non-root with no capability added, `exec-uid` is its own uid, the agent's state claim is not mounted into it (above), and the two containers share no process namespace. What the shape gives up is the uid boundary between an Exec child and the workspace process, so a child can signal the workspace server (`deployment.md:153` there).
  - **`shell_exec` needs two host requirements, both infra's** (`deployment.md:165-174` there). Every `shell_exec` call asks for an isolated network, which in this shape is a `CLONE_NEWUSER | CLONE_NEWNET` clone:
    - `user.max_user_namespaces` above `0` on every node that runs the workspace;
    - a `Localhost` seccomp profile admitting that clone, named on the **workspace container's** `securityContext` only, while the Pod and the agent container stay on `RuntimeDefault`. `RuntimeDefault` refuses the clone with `EPERM` before the sysctl is read, so the sysctl alone fixes nothing. `restricted` admits a `Localhost` profile. Rendering it is #348.
    - **Either one unmet, every `shell_exec` call is refused** (`agent_uid unavailable`), while Read, Write and List keep working, and nothing says so at startup. That is the lab today: its workspace container read `max_user_namespaces` as `0` and `unshare --user --net true` failed with `EPERM` under `RuntimeDefault` (gitops, 2026-10-10, sherlock#1049).
  - **`RLIMIT_NPROC` does not bind in this shape.** `sherlock` applies its 64-process limit only in the privileged drop (`deployment.md:418` there). The bound on an Exec child's processes is the container's pid limit, the cluster's kubelet `podPidsLimit`.
  - **A NetworkPolicy cannot stand in for the per-call network namespace.** The workspace shares the agent container's network, gateway included, and the gateway serves with `auth="none: loopback binds only"` (`deployment.md:53,230` there). Loopback traffic never reaches a NetworkPolicy, so only the per-call namespace keeps an Exec child off the agent's gateway (`deployment.md:165` there).
- It serves a directory on a claim of its own, `workspace`, which only its container mounts, at the path the agent mounts its state at, so the directory is `/var/lib/sherlock/workspace` and the agent's memory path does not exist in that container. The default it would otherwise take is relative and resolves, in an image that declares no working directory, against a root-owned directory the Pod's user cannot create in — so the container would exit before it listened.
- The agent's state — the memory store and the outbox beside it — is on the `state` claim, which only the agent's container mounts whole, so code the agent runs cannot read or overwrite it. A placed adapter mounts the outbox's subdirectory alone (ADR 0044, ADR 0060; `sherlock@44aaa55:docs/architecture/deployment.md` §Volumes and ownership, "Two writable volumes, not one shared filesystem"). Both claim templates are built whether or not a workspace image is named. The workspace's is sized by `spec.workspaceStorageSize`, and at `spec.storageSize` where that is unset; the renderer writes it from the profile's `workspaceStorageSize`. Both use `spec.storageClassName`, and a size either claim cannot follow is reported as `StorageSizeImmutable`.
- A StatefulSet whose workspace shares the state claim is replaced on the first reconcile that meets it, with no switch (ADR 0068). A StatefulSet created where none exists always gets the separate shape. That is an `Agent` with no adapter and nothing for the config file. A Pod carrying the adapter is released: the outbox init container is placed before it, so the kubelet leaves the adapter and the agent waiting.

So does a claim that is missing, differs from the UID the controller annotated on the Pod (`agent.garam.sh/pvc-uid`) when it first saw it running, or was created after the Pod. Without evidence, `WriterFence` is `Unknown` with the reason, the Pod is read again every 30 seconds, and no timeout releases it. With evidence, it is written to `status.writerStopped` first, then the next placement token is minted, then the finalizer is removed, and `WriterFence` is `True`.

Where the adapter is placed, a random token is minted into the Secret `<agent>-placement` before the first Pod, and again at each fence release before the next. The adapter alone mounts the Secret's projection, read-only, as it mounts the credential's (ADR 0073). `status.placement` and `status.writerStopped` are reports that the controller never reads back.
- Each placement of an agent with the adapter placed is registered with the control service, by the registrar (`internal/desired`, a `Runnable` beside the puller and the issuer, only where `--control-address` is set), at `POST /v1/operators/self/agents/{grn}/placements` under this manager's token for the control service (#212, #218).
  - **What a placement is to it.** It is the agent's Pod, not being deleted, in phase `Running`, carrying the claim UID the fence recorded (`agent.garam.sh/pvc-uid`) and the adapter. Agents a user wrote never register.
  - **The body**, all strings:
    - `epoch` is `spec.identity.assignmentEpoch`;
    - `podUid` and `pvcUid` are the Pod's;
    - `tokenSha256` is the hex SHA-256 of the placement token's bytes, read uncached;
    - `previous` is `null` for the first placement.
  - **The previous placement is read without reading status.** The release that mints the next token writes, in the same patch, two annotations on `<agent>-placement`: `agent.garam.sh/previous-pod-uid`, and `agent.garam.sh/previous-writer-stopped-sha256`, the hex SHA-256 over the RFC 8785 canonical JSON of the evidence that release recorded in `status.writerStopped`. The canonical form is `github.com/gowebpki/jcs` v1.0.2's, the maintained fork of the RFC author's reference implementation. A resumed release recomputes both and writes both again, so they agree.
  - **Once accepted.** A placement the control service accepted is not presented again. What was accepted is held in memory, so a restart presents each placement once more, which the control service answers as a repeat.
  - **Refusals.**
    - 409 `placement_superseded` or `epoch_superseded` is logged and the same body is never sent again. A new Pod, epoch or token is a new body.
    - Any other 4xx (403, `previous_mismatch`, `placement_conflict`, `evidence_missing`) is presented again after 5 minutes and counted in `garam_operator_control_refusals_total{route="placements",status}`.
    - A 5xx or no answer is presented again after a wait doubling from 1 to 30 seconds.
    - What is remembered is one placement per agent, started afresh when its body changes and dropped when the agent has no current placement.
- The manager reports the images it runs to the control service once, by the image reporter (`internal/desired`, a `Runnable` beside the registrar, only where `--control-address` is set), at `PUT /v1/operators/self/images` ([ADR 0074](adr/0074-report-each-operators-images-and-last-contact-to-a-console-read-of-the-control-service.md)).
  - **Configured images.** Each of `--agent-image`, `--agent-adapter-image`, `--agent-copy-image` and `--agent-workspace-image` that is set, as `agent`, `adapter`, `copy` and `workspace`, by the reference the flag names. A digest is given only where the reference ends in `@sha256:` and 64 hex digits.
  - **Its own image.** `manager`, read off its own Pod through the API server (`internal/desired/self`): the `manager` container's spec image, with the digest its status `imageID` ends in where that is a sha256 digest. The Pod is the one `POD_NAME` names, in `POD_NAMESPACE`. Where `POD_NAME` is unset or the read fails, the report goes without it, logged once, and nothing is made up.
  - **Retries.** A 5xx or no answer is sent again after a wait doubling from 1 to 30 seconds. Any 4xx is sent again after 5 minutes and counted in `garam_operator_control_refusals_total{route="images",status}`. The reporter ends once a report is accepted, so a changed image is reported by the restart that changes it. Where there is no image to report, no flag set and its own image unread, it sends nothing, logs that once, and ends.
- A person stops an agent without deleting it by setting `spec.suspended: true`, and starts it again by clearing it (ADR 0046).
  - **Whose field.** It is a person's. The renderer never writes it, and its writes carry the field manager `garam-operator-renderer`, so `managedFields` shows the person's manager owning `f:spec.f:suspended`.
  - **What it does.** The StatefulSet is asked for no replica, and nothing else changes. The StatefulSet controller deletes the Pod, and the writer fence releases it only on evidence, recorded in `status.writerStopped`. The `Agent`, its Secrets and both claims are kept.
  - **Resuming.** Clearing it asks the same StatefulSet for its replica, so the next Pod binds the same claims under the same UIDs.
  - **Status.** `Suspended` is `True` (`Suspended`) once the Pod is gone, `False` (`Suspending`) while it still exists, and `False` (`NotSuspended`) otherwise. `Available` is `False` with reason `Suspended` while the spec suspends the agent.
- The control service stops a managed agent without a replacement through `spec.stopped` ([ADR 0057](adr/0057-recover-an-agents-credential-through-a-prepared-request-and-stop-an-agent-without-a-replacement.md)).
  - **Whose field.** The renderer's. It writes the feed's `stopped` on every render, and clears it when the stop ends. The API server refuses it on an `Agent` with no identity, as it refuses `spec.revision`. `spec.suspended` stays the person's.
  - **What it does.** What `spec.suspended` does: no replica, the Pod released only on the writer fence's evidence, a Pod whose fence is `Unverified` held, and no replacement once it is released. `Suspended` and `Available` report it as they report a suspension, the message naming `spec.stopped`.
  - **Across a restart.** The renderer writes it again from the feed, and the reconciler reads it from the spec, so a manager restart keeps the agent at no replica. The puller renders an unchanged revision again when only the stop changed.
- The agent's state volume outlives the `Agent`. It is claimed through the StatefulSet's claim template, a claim template's PVC carries no owner reference, and this operator sets no `persistentVolumeClaimRetentionPolicy`, so Kubernetes' `Retain` default holds and the cascade that removes the workload does not reach the volume. The claim is named for the StatefulSet, which is named for the `Agent`, and a rendered `Agent` for the digest of its GRN, so recreating the `Agent` for the same GRN rebinds the same volume. That is what lets the feed's re-creation of an `Agent` deleted while its definition lives keep the agent's state, the memory store included, and it is why the volume is not taken with the workload: a `Delete` policy would turn that re-creation into the loss of the agent's memory. The workspace's claim is kept the same way.
- The reconciler writes an `Agent`'s status through a merge patch, which carries no resource version and names only the fields it decided, so a write landing between its read and its write does not fail the reconcile. Measured on `garam-dev` on 2026-08-26, one write racing each of 40 reconciles: an update was refused 27 times and a patch none.
- An Agent reports two conditions, and they answer two questions. `Synced` says whether the cluster carries the workload the spec asks for, and the reason where it does not. `Available` says whether that workload reports a ready replica. `status.observedGeneration` says which generation both answers were computed from, so a status the controller has not caught up with is visible as one. A spec this controller cannot act on is reported on `Synced` rather than returned as an error, because an error would requeue forever and say nothing on the object.
- `Available` is read off the StatefulSet the reconciler already holds, and off the revision of the Pod the writer fence already reads and watches, and is reported on a spec this controller cannot act on as readily as on one it can. A workload whose volume size the spec can no longer ask for is still running, and a reconcile that reads the object anyway can say so for nothing; what it may not do is fetch something to answer, because a condition worth a second read is worth a watch instead.
- What this operator guarantees is still about the declaration. `Available` widens what is reported and not what is promised: a replica is ready once its containers are running, this workload carries no readiness probe, and a container running the wrong binary is ready on those terms like any other. Issue #3 records that a broken agent inside a running Pod is invisible from here, and this condition does not close that — the boundary is written into the condition's own message, which is where a reader of `kubectl describe` meets it rather than in a document they will not open.
  - **The state volume's health is not among them.** `Synced` says the cluster carries the workload the spec asks for, and a claim's binding is not part of that judgement: the claim is asked for and found, and the volume behind it is not asked about. Measured on `garam-dev` on 2026-08-24 (#72), a claim whose backing device had gone read `Bound` while its Pod ran and restarted zero times, so `Synced=True` would have stood against a state volume that was dead, and the failure presents as the agent's. The operator holds no instrument for that state: it reads the claim and the Pod, and reads nothing that says whether the volume behind the claim is alive.
- **Only the condition types this operator writes stay on an Agent** (#341). Its status write keeps `Synced`, `Available`, `Recovery`, `Suspended`, `WriterFence` and `MemoryMove`, the list in `internal/controller/agent_status.go`, and drops every other type on the next reconcile. A type the operator stops computing therefore leaves every Agent without a separate step. That is how `StateIsolated`, removed by ADR 0068 and computed nowhere since, left the lab's Agent: it kept `StateIsolated=False SharedClaim` on a workload whose claims were separate.
- **A Pod on another revision than its StatefulSet's is rolled, and neither condition reports it reconciled** (#340).
  - **When.** The Pod's `controller-revision-hash` is not the StatefulSet's `status.updateRevision`, and the StatefulSet's status has observed its generation.
  - **What the operator does.** Where the StatefulSet owns the Pod, the operator deletes it with an ordinary delete, preconditioned on its UID and never forced, and ADR 0042's fence holds it until its writers stop. A Pod the StatefulSet has not adopted yet is left for it to adopt.
  - **What is reported.** Until a Pod on the update revision exists, `Synced` is `False` (`WorkloadRolling`) and `Available` is `False` (`ReplicaOutdated`), both naming the two revisions.
  - **Before the status is current.** Where a Pod exists and the StatefulSet's status has not observed its generation, or names no update revision, the revision the Pod should run is not known yet. Nothing is deleted, `Synced` is `False` (`RolloutNotObserved`), and `Available` is `Unknown` (`RolloutNotObserved`), since the replica counts are as stale. A replacing StatefulSet is in this state beside the Pod it is about to adopt until its controller first writes status.
  - **Never reconciled.** In neither state is the workload reported reconciled. Only no Pod, or a Pod on the update revision, reads as reconciled. A held-stopped agent asks for no replica, so its Pod is released rather than rolled, and its conditions say so.
  - **Why the operator acts.** A StatefulSet that replaced a shared-shape one adopted the old Pod, recorded `currentRevision == updateRevision`, and never rolled it, while both conditions reported success (lab, manager `4c425a7`).
- A reconcile that stops before reconciling a workload reports `Available` as `Unknown`, not `False`. It read no StatefulSet, and an Agent whose Secret was deleted after its workload was built still has that workload running, so `False` would be a claim about something this operator did not look at.

### Copying an agent's state

A consistent copy of an agent's state is taken through `spec.suspended`, and only from a writer that drained and positively stopped, as `sherlock@b3c05c2:docs/architecture/deployment.md` §Snapshot and restore requires. Its procedure is `deploy/runtime-fixture/snapshot.sh` (`copy`, `verify`, `restore`).

1. **Suspend.** Set `spec.suspended: true` on the `Agent`.
2. **Wait for both signals.** The copy is taken only once `Suspended` is `True` **and** `WriterFence` is `True` with reason `WriterStopped`, its evidence recorded in `status.writerStopped`. `Suspended` alone says the Pod is gone, and a Pod a person released by hand leaves no evidence.
3. **Copy.** Copy the claim the memory is on, `state-<agent>-0` or the end of its `agent.garam.sh/moved-to` chain, with Sherlock's procedure, from a Job that mounts the released claim. Nothing else mounts it while the agent is suspended. The workspace claim is not part of the agent's state.
4. **Resume.** Clear `spec.suspended`. The agent starts again on the same claims and the same credential.

An agent whose StatefulSet still shares one claim is replaced on the first reconcile of a manager carrying ADR 0068, keeping its `state` claim by name, with a new, empty workspace claim. An `Agent` stored with a model other than `mock` and no embedding is still suspended, edited and reconciled after the CRD upgrade (§the model above, #289).

### Moving an agent's memory

A person moves an agent's memory to a new claim with `spec.memoryMove: {id, storageClassName, storageSize}`. The manager then runs the whole move, in [ADR 0065](adr/0065-move-an-agents-memory-only-through-a-verified-copy-it-accepts-before-it-serves.md)'s order:

1. **Stop.** The agent is stopped, and the writer fence releases its Pod.
2. **Check the drain.** The fence recorded the agent's exit on the claim, as `agent.garam.sh/last-writer`, and the move goes on only if that exit was 0.
3. **Copy.** A Job copies `memory.db`, `-wal`, `-shm` and `outbox/` into `<agent>-state-<id>`.
4. **Verify.** A second Job compares both claims' SHA-256 manifests.
5. **Switch.** The agent starts on the copy with `--require-store`.
6. **Accept.** The agent's first Pod on the copy is Ready.

`MemoryMove` reports each step. It is `True` with reason `Accepted` once the agent accepted the copy.

- **Before you move.**
  - **Agent version.** A move needs agent v0.2.0 or later. An earlier image refuses `--require-store`, and the move is refused `AgentRefusedStore`.
  - **Separate claims.** The agent must claim its state and its workspace separately, or the move is refused `SharedClaim`. The replacement gives a shared-shape agent separate claims on its first reconcile ([ADR 0068](adr/0068-keep-no-backward-compatibility-path-during-development.md)), so the refusal meets only a move asked of an agent before that.
- **When the drain was not clean.** A move refused `WriterNotDrained` found that the last writer did not exit 0, or that its exit was never seen: cut by SIGKILL at the grace period, released by hand, or never started. To move such an agent:
  1. clear `spec.memoryMove`;
  2. let the agent run, and stop cleanly once;
  3. then set the move again under a new id.
- **When a move is refused.** The agent stays stopped on the claim it was on, and no step writes that claim. The refused target is kept, annotated `agent.garam.sh/move-phase: refused` with its reason, and its id is never used again. Clearing the move starts the agent on its old claim; a new id tries again.
- **After a move.** The claim the memory moved off is kept and stays allocated. Deleting it is a person's step, once `MemoryMove` is `Accepted`. Its name and UID are on the target claim, as `agent.garam.sh/move-source` and `agent.garam.sh/move-source-uid`. Clearing `spec.memoryMove` afterwards changes nothing: the claim moved off names the claim moved to, as `agent.garam.sh/moved-to`, and that chain, which outlives the Agent as its claims do, decides the claim the memory is on.
- **No integrity check runs.** The copy is verified byte for byte against a source the agent closed cleanly. No image this operator deploys carries SQLite to run `integrity_check`.

## Rationale

The layout and the generated manifests follow the scaffold, per [ADR 0001](adr/0001-kubebuilder-go-v4-scaffold.md): code is written to fit the CLI's paths rather than the CLI's output being reshaped to fit a preferred layout.

The workload's form is [ADR 0005](adr/0005-statefulset-of-one.md): a StatefulSet of one replica, because the agent's state is a single-writer store and the ordering guarantee is the only thing keeping two writers off one volume.

The image field was settled on issue #11, before the API was written, and carries no ADR: the rule is stated in the field's own doc comment, where it is enforced. "No outbound call in `v1alpha1`" was settled there too, as a milestone boundary rather than a project rule. ADR 0007 is where that boundary was crossed, and no field of the API moved when it was — which is what the boundary was drawn for.

The Pod's group and the group-readable mode are [ADR 0006](adr/0006-credential-group.md), settled on issue #31 after the e2e layer measured what no layer below it could see: a container that drops root cannot read an owner-only file the kubelet wrote as root. Its erratum of 2026-08-23 narrows what the group reaches, without moving the decision.

How a file its reader must own reaches that Pod is [ADR 0010](adr/0010-copy-an-agents-credential-into-a-memory-volume-the-pods-own-user-owns.md), settled on issue #82 once `garam` published the rule as a contract and refused the branch where the reader narrows it. It does not supersede ADR 0006 and nothing in ADR 0006 is false: that decision carries the projection into the Pod, and this one carries it from the projection to a reader that must own it. It is also where ADR 0006's rejected uid field is reopened and rejected again, for a second reason — the operator names the Pod's user instead of being told the image's. Its shape was measured on `garam-dev` under PodSecurity `restricted` before it was built, with two controls that separate the rule's two halves. [ADR 0073](adr/0073-give-every-agent-garam-tokens-its-assignee-mints-in-place-of-a-certificate.md) supersedes it: the tokens that replaced the certificate are read by an adapter that does not check their mode, and are refreshed in the running Pod, which a copy made once at start cannot follow.

How the operator reaches `garam` is [ADR 0007](adr/0007-claim-definitions-from-a-poller.md), settled on issue #2 once `garam`'s own ADR-0033 decided the surface: a poll rather than a watch, a claim that binds the operator to the agent GRN a definition minted, and a second claim that is a conflict rather than an override. What it decides here is the division between what a definition says and what this operator builds, where the poll runs, what the operator authenticates as, what it verifies `garam` against, and where a claimed GRN is reported. Its Context listed five values keys as the ones `garam` expects; its erratum of 2026-09-27, from issue #155, records that the list was read off a schema example and `garam` publishes none. The division stands without it. That composition is `garam`'s, held as a definition's `values`, is superseded by ADR 0032, and the poller and its claim by ADR 0077, once garam `v0.5.0` served no definition; the division between what a definition says and what this operator builds stands.

How the operator authenticates to `garam` is [ADR 0072](adr/0072-authenticate-the-manager-and-the-control-service-to-garam-with-their-own-private-keys.md), settled on issue #354 once `garam` `9ba35c3` (garam ADR-0102) let a registered operator prove its identity with a key it is issued and exchange it for short-lived tokens. It supersedes [ADR 0008](adr/0008-renew-the-operator-credential-into-the-secret-it-is-read-from.md), which renewed the operator's certificate into the Secret it was read from; [ADR 0022](adr/0022-end-the-enrollment-on-a-certificate-that-has-not-expired.md), which with [ADR 0020](adr/0020-enroll-this-operator-with-a-one-time-token-and-keep-the-key-it-generated.md) and [ADR 0021](adr/0021-present-any-one-enrollment-token-once-and-wait-for-another.md) before it had the operator enrol for its first certificate; and the certificate-expiry gauge of [ADR 0030](adr/0030-carry-the-operators-certificate-expiry-and-garams-refusals-as-metrics.md), whose refusal counter stands with its labels amended. A key `garam` issues and a person places leaves nothing for this operator to write, which is what removes the Secret's write path and its RBAC; the exchange-failure counter takes the expiry gauge's place as the notice ahead of failure. No dual mode is kept ([ADR 0068](adr/0068-keep-no-backward-compatibility-path-during-development.md)), and the agents' own credentials move to tokens in #355.

How a sustained loss of that authentication is seen is [ADR 0075](adr/0075-hold-the-manager-and-the-control-service-not-ready-while-their-garam-authentication-has-failed-for-an-hour.md), settled on issue #381 after `garam` refused the operator on aurora for three days with nothing scraping its counters (#380). Readiness is the one signal Kubernetes carries that needs no RBAC, no metrics stack and no object the operator owns, and it reaches the control service too. The bound is one token lifetime: a held token rides out failed refreshes for a third of one, and the identity call and the 30-second keep bring a new outcome every five and a half minutes at the latest. A refused call ends only at an accepted one, because #380's signature is `garam` refusing every call while every exchange succeeds. A Warning Event, a condition on the `Agent`s and a liveness failure were rejected there.

How an agent authenticates to `garam` is [ADR 0073](adr/0073-give-every-agent-garam-tokens-its-assignee-mints-in-place-of-a-certificate.md), settled on issue #355 once `garam` `afde8b8` (garam ADR-0100) let an agent's assignee mint its tokens and gave the adapter a token mode that reads them from files before every call. It supersedes [ADR 0010](adr/0010-copy-an-agents-credential-into-a-memory-volume-the-pods-own-user-owns.md), [ADR 0059](adr/0059-place-a-recovered-credential-beside-the-kept-issuer-only-once-it-verifies-against-it.md) and [ADR 0062](adr/0062-write-the-chain-garam-answers-a-recovery-with-and-verify-the-recovered-leaf-against-it.md), and the certificate parts of ADR 0009, ADR 0034, ADR 0042, ADR 0057 and ADR 0072. What it decides is who mints an agent's tokens (this operator, on either source), where they are kept (the credential Secret, which the adapter alone mounts), when they are refreshed (in `garam`'s window, under the version read) and what proves the controller at activation (`garam`'s answer about the agent's own token, in `control.md`). The boundary it draws is the container mount and not the file mode, because every container of the Pod runs as one user.

What a claimed definition becomes is [ADR 0009](adr/0009-construct-a-claimed-agent-from-the-operators-own-configuration.md), settled on issues #75 and #79 together because neither can be built without the other's answer: an `Agent` needs an image, a storage size and a credential, and a definition carries none of the three. It decides where the first two come from, when the certificate route is called and what becomes of the answer, who names the objects, and where the epoch is met. Its route was measured on `garam-dev` before it was built, which is where the facts about the two roots, the unfenced re-issue and the unbranchable refusal come from. Its certificate route and the credential it placed are superseded by ADR 0073, where the mint takes the route's place and proves the same epoch, and the construction of a claimed agent by ADR 0077. That the image is this operator's configuration stands.

That the image is maintained rather than only written is [ADR 0018](adr/0018-keep-the-image-of-an-agent-this-operator-constructed-current-with-its-own-configuration.md), settled on issue #121 after a corrected `--agent-image` was applied and repaired nothing. It extends ADR 0009 rather than superseding it: that decision put the image in this operator's configuration and made this operator the only writer of the field, and this one is what follows from being that writer. What it adds is which agents the correction reaches, what tells them apart, where it runs, and what it does not take with it. The distinction it rests on was measured on `admin@garam-dev` before it was built, and the cost of not having it was measured on the same cluster. The constructor's correction is superseded by ADR 0077: the renderer writes the image on every render.

Where an agent's tool set is declared is [ADR 0012](adr/0012-declare-an-agents-tool-set-in-its-definitions-values.md), settled on issue #92. It extends ADR 0009 rather than superseding it: the sentence "no value of a definition names either, and none is read" decides the image and the storage size, and its reason — the audience a container choice asks — does not reach a value that chooses among the tools an image already carries. What it adds to the division is the other half of it: which values this operator carries, what becomes of the ones it does not, and how one reaches a Pod. It landed with no mechanism and nothing here reads a value yet, because both peer projects sequenced the declaration site ahead of the code that would carry it. Its declaration site, a `garam` definition's `values`, is superseded by ADR 0032, which moves the key family to the control store's desired definition; how a pin set reaches the Pod stands.

How the tool set an agent loads reaches its Pod is [ADR 0027](adr/0027-an-agents-tools-arrive-in-its-own-image-and-this-operator-mounts-no-tool-tree.md), settled on issue #173, which supersedes [ADR 0019](adr/0019-mount-an-agents-tool-tree-from-an-image-this-operator-names.md). ADR 0019 mounted a tree from an image this operator named because the agent image then shipped none; `sherlock` has since baked its tools into that image (`garamsh/sherlock#852`) and the tools image no longer exists, so ADR 0027 builds no tree and leaves the directory to the image. It answers issue #142's question whether a tools image exists. ADR 0012 stands under both: the directory is no definition's key, and what moved is only who writes it.

What renders a declared tool set into the Pod is [ADR 0024](adr/0024-write-an-agents-config-file-from-an-init-container-into-a-directory-this-operator-names.md), settled on issue #139, which is the one thing ADR 0012 named as left to its implementation issue. It extends ADR 0012 and supersedes nothing: that decision settled the key family, the closed set, the file and its mode, and this one settles what writes the file and where the agent finds it. Its ground is a measurement rather than a preference — a ConfigMap does not remove the container that has to write the file, because a Pod carrying a group cannot be handed an owner-only file by the kubelet — and the discovery road it takes is the one whose directory this operator can name. What it could not exercise is recorded with it: envtest has no kubelet and the e2e suite runs a substitute image, so the log line that says an agent runs unpinned has not been seen to stop.

What is supported is [ADR 0031](adr/0031-support-agents-declared-in-garam-on-one-cluster-of-the-sherlock-type.md), set by the owner on issue #202. It supersedes nothing: that agents are declared in `garam` is ADR 0007's division, the types on hold stay where ADR 0025 and ADR 0029 put them, and a hand-written `Agent` is still reconciled as `delivery.md` records. What it adds is which of the shapes those decisions allow is supported, why declaring `Agent`s in the cluster for `garam` to observe was not taken — it would move identity, per-agent certificates and single ownership out of `garam` — and what would reopen each point. Its §1, that agents are declared in `garam`, is superseded by ADR 0032; §2 to §4 stand.

Who owns an agent's desired definition is [ADR 0032](adr/0032-own-an-agents-desired-definition-in-this-projects-control-service.md), recorded on issue #205 from the separation of services the owner accepted on `garamsh/garam#1155`. It moves the definition, its templates and its revisions to this project's control service and leaves the GRN, authorization and collaboration with `garam`, superseding ADR 0007's composition, ADR 0012's declaration site and ADR 0031 §1 and nothing else. It keeps what ADR 0031 refused to give up: identity, the certificate route and the claim's epoch stay `garam`'s, and an `Agent` is rendered rather than a source. It decides ownership and invariants only, and the wire contracts are agreed elsewhere.

What carries an agent's model and ego is [ADR 0035](adr/0035-carry-an-agents-model-and-ego-in-its-spec-and-render-them-through-its-types-descriptor.md), settled on issue #151 once the PM narrowed it to `sherlock` and put the settings on `AgentSpec`. It extends ADR 0024 with a second key family and a second file, and ADR 0029 with three descriptor fields, and supersedes nothing. The separate `Model` kind the issue first asked for was not built: the desired source is to move to the control store (ADR 0032), and a kind here would be a second one.

Where an agent's identity is carried is [ADR 0037](adr/0037-carry-an-agents-identity-in-its-spec-and-start-the-agent-under-it.md), settled on issue #219 once `sherlock@0ced773` made `--agent-id` required and `garam`'s adapter required the GRN. Rendering the identity into the Pod made it a reconcile input, which `stack-kubebuilder.md` §3 keeps out of Status, so it supersedes in part ADR 0007's "never written in `AgentSpec`" and ADR 0016's equivalent for the epoch: both are still reported, and the spec carries the rendered copy. It replaces ADR 0035's ego-only argument renderer with one carrying the agent ID, the ego and the epoch.

How the manager takes desired state from the control service, and how it keeps a GRN on one source, is [ADR 0043](adr/0043-pull-managed-agents-desired-state-from-the-control-service-and-keep-each-grn-on-one-source.md), the first slice of issue #217. It puts the consumer in a domain of its own, `internal/desired`, and moves the names the GRN derives below both sources into `internal/agentname`. It marked each `Agent`'s source when the `Agent` was built rather than reading status; [ADR 0077](adr/0077-build-agents-only-from-the-control-services-feed-and-remove-the-legacy-path-and-the-cut-over.md) removes the marker with the only other source, so `spec.identity` alone marks an `Agent` the control service holds.

Why a managed agent's definition revision is in its spec and its config file is [ADR 0054](adr/0054-carry-a-managed-agents-definition-revision-in-its-spec-and-render-it-into-its-config-file.md), from issue #291: without it `sherlock` reported an empty `config_revision`, and the activation route refused every activation bound to it. It is a typed spec field, refused off the `Control` source, rather than an annotation or a field under `spec.identity`.

Why the agent accepts garam's signed messages through one static `issuers` entry is [ADR 0071](adr/0071-render-garams-issuer-into-a-managed-agents-config-and-let-the-agent-fetch-its-keys.md), from issue #337. Without the entry, `sherlock` `v0.3.0` refuses a signed message `403 signature rejected: issuer`. It keeps no key-copying loop: `sherlock` fetches and refetches the set itself under a root it is told, which `garamsh/sherlock#1008` added for this and `v0.4.0` released.

Why a writer the kubelet never created counts as stopped only in a Pod the kubelet made terminal is [ADR 0061](adr/0061-release-a-pod-whose-writers-were-never-created-only-on-the-kubelets-terminal-phase.md), from issue #311: an empty container ID can be a stale status, or a container the runtime no longer lists, while the kubelet's terminal phase follows its own check that nothing of the Pod runs. Its erratum, from issue #363, records that a Pod with no init container never reaches that shape, and is held.

What holds an agent's next Pod off its volume until the last one's writers stopped, and what the adapter is given per placement, is [ADR 0042](adr/0042-fence-each-agent-pod-on-positive-evidence-its-writers-stopped-and-mint-an-adapter-only-placement-token.md), the first slice of issue #212. It supersedes this document's statement that the reconciler holds no finalizer: an `Agent` must outlive its Pod for the Pod's evidence to be persisted first. It keeps the claim's baseline on the Pod rather than in status, because the reconciler reads no status as an input. It states the one window a hand edit leaves: a claim recreated within the same second as the Pod's creation. Placement registration with the control service, leaf re-presentation, and the adapter's setting for the token wait on #218 and garam#1169.

How long an agent Pod is given between SIGTERM and SIGKILL is [ADR 0064](adr/0064-give-an-agent-pod-the-grace-period-one-full-step-of-its-drain-needs.md), from issue #282: measured on Kind against the `v0.2.0` image, which showed that the drain waits for the step in flight and that the commit costs milliseconds. One full step is covered, and a worst-case turn is not, because the fence would hold every replacement for as long.

How an agent's memory moves to another claim is [ADR 0065](adr/0065-move-an-agents-memory-only-through-a-verified-copy-it-accepts-before-it-serves.md), from issue #296, as the managed counterpart of garam's ADR-0089. The move is a person's field for the reason suspending is. The copy is verified by digests the manager compares itself, before the agent starts on it. The agent's own `--require-store` is the acceptance. garam is asked for nothing beyond the activation it serves.

Who gives an agent garam's reply instruction, and how, is [ADR 0041](adr/0041-join-garams-reply-instruction-to-the-ego-wherever-the-adapter-is-placed.md), settled on issue #236 once `garam` pinned the `garam-message.v1` envelope. The manager joins it to the ego wherever it places the adapter, because only it knows when an envelope arrives and because the ego a person edits should hold only their text. The control service adding it to every definition was refused on both grounds. That an agent with no declared ego loses `sherlock`'s default there is the price it records.

Where that instruction now goes is [ADR 0045](adr/0045-give-garams-reply-instruction-as-an-operator-instructions-file.md), settled on issue #239 once `sherlock` took operator instructions beside the ego (`garamsh/sherlock#949`, `a44bbaa`). It supersedes ADR 0041: the instruction is an operator instructions file and the ego is the author's alone. Its switch, `--agent-instructions-file`, and the joined ego it kept as the switch's off state are superseded by [ADR 0068](adr/0068-keep-no-backward-compatibility-path-during-development.md).

Where `garam`'s adapter runs is [ADR 0034](adr/0034-place-garams-adapter-as-a-native-sidecar-beside-every-agent-this-operator-constructed.md), settled on issue #216 once `garam`'s PM confirmed the split: `garam` owns the command and everything it does with a message, and this operator owns its placement. It follows ADR 0023's shape — an image the deployment names for a thing the workload carries, and an unset flag that builds the Pod built before — and ADR 0037 is what gives it the GRN it needs without reading a status. What it leaves unbuilt is recorded with it: the placement token (#212) and the outbox mount.

What `spec.type` decides is [ADR 0025](adr/0025-generalize-the-agent-kind-by-agent-type.md), settled on issue #169: one kind, a closed set of types, and a per-type table in the controller. What that table carries is [ADR 0029](adr/0029-route-every-agent-specific-name-in-the-pod-through-its-types-descriptor.md), settled on issue #176, which extends ADR 0025: the two fields ADR 0025 named could not produce sherlock's variable names or its file, so the descriptor holds every name itself, and the Pod builder holds none.

What serves an agent's files and runs its commands is [ADR 0023](adr/0023-run-an-agents-workspace-as-a-second-container-this-operator-names.md), settled on issue #153 after that issue's own premise was measured and failed. It took ADR 0019's shape — a second image the deployment names for a thing the workload carries and no `Agent` names — which ADR 0027 has since retired for the tool tree and which stands for the workspace; it supersedes nothing: ADR 0005 keeps its single replica, and ADR 0010 is why the uid the workspace is told is 65532 rather than the 1001 its image would take. What the issue was opened on, that the container needs `SYS_ADMIN` and so a namespace at a level admitting it, was received through a third party and is false at the uid this Pod runs; what stood in the way was that no container was built at all.

Where the workspace's files are kept is [ADR 0044](adr/0044-give-an-agents-state-and-its-workspace-separate-claims.md), settled on issue #249 after the gitops PM measured the workspace's exec uid reading and appending to the agent's memory store through the claim the two shared (gitops #288). It supersedes ADR 0023's workspace on the state volume and nothing else of it, and closes the open question of whether the two could share one volume's size. It keeps ADR 0042's fence across the StatefulSet's replacement rather than adding one.

Why no switch stands between a deployment and that replacement, the assignment epoch, the instructions file or a managed agent's control settings is [ADR 0068](adr/0068-keep-no-backward-compatibility-path-during-development.md), the owner's directive of 2026-10-09 (#327): during development only the correct structure is kept, and no path for an earlier version of this operator or of the images it runs. It supersedes ADR 0047, ADR 0045's and ADR 0049's switches, ADR 0037's epoch flag, ADR 0044's workspace seed, and the `GATEWAY_AGENT` setting ADR 0049 kept for `garam@fdfb76d`. The owner decided the replacement keeps the state claim by name and gives the workspace a new, empty claim. A deployment runs `sherlock` `v0.2.0` or later, the oldest that accepts every argument this manager passes, and an adapter of `garam@e81a1e0` or later.

Why every placed adapter, legacy included, is given the outbox is [ADR 0060](adr/0060-give-every-placed-adapter-its-agents-outbox-on-either-source.md), from issue #310: a legacy agent's replies never left its Pod, and the pinned adapter forwards a legacy outbox. ADR 0077 removes the unfenced adapter, so every placed adapter now has the outbox beside the control settings.

What a managed agent's adapter is told about the control service, and how it reaches the outbox, is [ADR 0049](adr/0049-give-a-managed-agents-adapter-the-control-services-settings-behind-a-switch.md), settled on #218 once `garam@e81a1e0` merged the adapter's side of agent-execution.v1. Its switch, `--agent-adapter-control`, is superseded by ADR 0068, which gives every managed agent's adapter the settings; it gives the adapter the outbox alone and no other part of the state claim ADR 0044 reserved for it, and closes the open question of how the adapter reaches the outbox.

Where the agent's memory store lives was settled on issue #157, and carries no ADR because it changes no rule: ADR 0005 already puts the agent's state on the claimed volume, ADR 0029 already routes every name the agent reads through the descriptor, and ADR 0023 already keeps the two processes to disjoint subtrees. What it corrected is a fact. Until then no agent this operator built wrote the volume: `sherlock`'s relative default put the store under `/home/nonroot`, and on 2026-09-06 the first agent constructed in production had nothing of its own on the volume. ADR 0005 carries an erratum saying so. Mounting the volume at `/data`, where the agent image's own comment points, was refused: the default resolves against `/home/nonroot` and not `/data`, so that mount would have stayed as empty. Nothing is migrated, because the production reading found nothing to move.

That the agent's state volume outlives the `Agent` was settled on issue #152 and carries no ADR because it changes no rule: it is what ADR 0005's claim template does once ADR 0009 names a constructed `Agent` for its GRN, and what is recorded is that the retention default is kept on purpose rather than left unset by omission.

Where the flags carrying all of this are set is [ADR 0013](adr/0013-the-base-carries-what-every-deployment-shares.md), settled on issue #105, and `configuration.md` is where it is described: the Secret and the four credential paths are the base's because the mount they read is, and the address, the agent image and the storage size are the deploying overlay's.

The condition this API reports was settled on issue #14, and carries no ADR for the same kind of reason: its type and its reasons are constants in `api/v1alpha1`, and the field's own doc comment names them where a user of the API reads them.

The second condition was settled on issue #103 and carries no ADR either. What it reports was decided in issue #3 clause 5, that CR status carries Pod state, and this is that clause implemented rather than a decision taken here; what is chosen is the name, and Kubernetes chose it first — a Deployment splits the same question into `Progressing` and `Available`, and this operator's `Synced` already holds the first half. `Ready` was the other candidate and is a Pod's word for its own containers, which on an `Agent` would read as a claim about the agent. The reasons and the sentence bounding what a ready replica is worth are constants and a message in `api/v1alpha1`, which is where issue #14 put the first condition's.

What the workload's security context carries was settled on issue #85 and carries no ADR: `restricted` is a published standard rather than a choice this project makes, and the four fields it asks for were left undecided by ADR 0006 on a ground — that each constrains what a user's image may be — which holds for one of them and not for the four. That one is left open below.

That every container pulls at every start was settled on issue #99 and carries no ADR: the value follows from a requirement `sherlock` published rather than from a choice made here, as `restricted` did on issue #85. What is settled beside it — that `spec.image` accepts a tag — moves no rule either. The field accepted one before, and what accepting one costs is stated in the field's own doc comment, which is where issue #11 put the field's rule.

What this operator tells `garam` about an agent's pod is [ADR 0016](adr/0016-report-what-the-operator-observed-and-stay-silent-where-it-observed-nothing.md), settled on issue #117 once `garam` published a route for it. It decides four things that depend on each other in that order: where the epoch lives between the claim and the report, which of `garam`'s four states this operator can honestly reach, when a report is sent, and what a refusal does. It closes the open question ADR 0007 left about what this operator reports back, for the provisioning half of it. Its route was read at `garam@e1e69fd` and every report in this repository's tests is served by a stub listener, because `admin@garam-dev` is read-only for this project. It is superseded by ADR 0077, which removes the report with the legacy path: the reporter never reported an agent the control service holds.

That the reconciler writes an `Agent`'s status through a patch was settled on issue #84, while the poller also reported the GRN there, and carries no ADR because it changes no division. ADR 0077 removed the poller, and the patch stays. It is recorded here because the reasoning that cleared the race in review — that disjoint fields do not race — was wrong, and the first live run is what found out; the next claim about which writes race on this object is to be tested against a cluster.

Stopping an agent without deleting it is [ADR 0046](adr/0046-suspend-an-agent-from-a-field-a-person-owns-and-release-its-pod-only-on-the-writer-fences-evidence.md), settled on issue #254. The field is a person's because a stop for a copy is an operator's act on one copy of an agent, not part of its definition. The Pod goes through ADR 0042's fence because a scale-down deletes it like any other deletion.

Why the manager builds agents only from the control service's feed is [ADR 0077](adr/0077-build-agents-only-from-the-control-services-feed-and-remove-the-legacy-path-and-the-cut-over.md), from issue #388, once garam `v0.5.0` (`72e9369`, garam ADR-0118) removed legacy execution and the certificate path, and the owner directed that every legacy path here go with no migration. With no second source, `spec.identity` is what marks an `Agent` the control service holds, every placed adapter is fenced, and the poller, the constructor, the reporter and the flags only they read go. A person's `Agent` with no identity is supported as before.

## Open questions

- **What this operator reports back to `garam`.** Nothing, since ADR 0077 removed ADR 0016's provisioning report with the legacy path that alone sent it; whether a managed agent's provisioning state should reach `garam` is undecided. Runtime state is the agent's own account of itself and is reported on a route this operator is refused, so it is not this operator's to send and no agent image exists to send it. ADR 0012 gives the question a second subject that no route touches: a value this operator ignored is reported in this operator's log and a pin an agent cannot satisfy in the agent's, and neither log is one a definition's author reads.
- **Whether `failed` should become reachable, if a provisioning report returns.** It is the state `garam` most wants and the one this operator cannot earn from a replica count. Reaching it means reading Pods, which issue #72's ruling makes a watch rather than a second read, and it would move the `Available` condition and the sentence bounding it as much as the report — telling a replica that cannot start from one that has not started yet is a change to what this operator observes, not to what it says. What would settle it is a deployment that has to act on the difference; `garam` publishes nothing an operator should do about `failed`, which is the same gap this document records for a reassignment.
- **Whether a model's key can be kept from the tools an agent spawns.** ADR 0035 places it in the agent's environment because `sherlock` reads it from nowhere else, and `sherlock` hands that environment to every tool. Narrowing it is `sherlock`'s change — a key read from a file, or a runner that strips the variable — and what would settle it is `sherlock` offering either.
- **Whether an agent's required tool set should be reachable from configuration at all.** Nobody has answered it. `sherlock` holds the invariant deliberately, which is why the required set exists, and has not decided that reaching it from no configuration is right; this operator has no basis to decide that for them, and reads no key for something it could not deliver. What would settle it is an agent whose author needs to see or change the required set, rather than an operator asking for the switch on principle.
- **What else runs beside the agent in the Pod this operator builds.** Half of this is answered: `sherlock`'s workspace is a second container and this operator builds it, per ADR 0023. The other half is not. `garam`'s adapter is the third, and this operator builds it, per ADR 0034. What an agent image is expected to already contain, beyond running as the user the Pod names, is still not stated anywhere this repository can point at.
- **What an operator does when it learns it no longer holds an agent it is running.** The refusal reaches this operator at the agent's next refresh, where it is reported by name, and it acts on nothing else: `garam` publishes nothing that says an operator should stop. Whether the workload should be torn down, reported on, or left is undecided, and what would settle it is a reassignment happening to a running agent rather than to a test row.
- **No `garam` process reads the token files this operator writes, at any layer here.** The integration layer has no kubelet, and the e2e suite runs a substitute agent image and names no adapter image, so that the kubelet's swap reaches the adapter's file and the adapter reads it is `garam`'s contract, not a measurement here. `Available` reports green over that same substitute rather than over an agent — a stand-in the suite builds from `test/e2e/agent-image/`, which accepts the command line this operator gives `sherlock` and refuses one with no agent ID — so it adds a layer that reads green and not an execution. What would settle both is a bring-up with `garam`'s adapter image.
- **Whether the agent's uid can execute the tools it is given.** The tools arrive in the agent's image, owned by uid 65532 (`sherlock@35e79b5:build/agent.Dockerfile:70-74`), and the Pod runs as that uid, but no layer in this repository executes one: the integration layer has no kubelet and the e2e suite runs a substitute image. What would settle it is a bring-up of a published agent image.
- **Whether an agent's workspace can isolate an exec on the nodes this operator builds for.** The unprivileged path `sherlock` takes at a non-root user clones a user namespace, which needs unprivileged user namespaces enabled on the node — `sherlock` refuses the call where they are not — and which the seccomp profile this Pod names may or may not permit; nothing in this repository can answer either, because envtest has no kubelet and the e2e suite runs a substitute image. Both bound the isolated subset only: a call that does not ask for network isolation reaches neither, and both present as a refused exec rather than as a Pod that fails to start. What would settle it is one exec, asking for isolation, on a node of the deployment's own.
- **Whether an agent's image may write its own root filesystem.** `readOnlyRootFilesystem` is the part of the Pod's security context ADR 0006 left undecided that issue #85 did not settle with the rest. It is no part of PodSecurity `restricted`, so nothing refuses the workload without it; the manager sets it on itself and this operator sets it on none of the containers it builds, because the field constrains what an image needs rather than what it is allowed to do and no image in the Pod is this operator's — the agent's is the deployer's or the user's, and the copy tool's is the deployer's, asked for a shell, `install` and `mkdir`, and nothing more. Setting it on the init containers alone would buy a guarantee about filesystems discarded when those containers exit, at the price of another clause on `--agent-copy-image`. What would settle it is a deployment that has to refuse an agent image the right to write its own filesystem.
- **What a corrected image costs an agent that is running.** Bringing `spec.image` current rolls the StatefulSet's replica, so an agent holding a session loses it without being asked. Nothing drains it first: this operator reads a replica count and no readiness probe, and `garam` publishes no route that asks an agent whether it may be replaced — the same gap issue #3 records one layer out. ADR 0018 accepts that price against an agent that otherwise never runs at all, and answers nothing about an agent that is working. What would settle it is a route that says whether an agent is busy, or a deployment that has to correct an image without interrupting one.
- **Whether any signal short of a write distinguishes a working state volume from one in `shutdown` state.** A mounted ext4 whose backing device disappears enters `shutdown` state: reads may still be served from page cache, and writes return `I/O error`. Every indicator this operator holds reads green against it — the claim is `Bound`, the Pod runs, `Synced` is `True` — and the failure presents as the agent's (#72). Whether a node mount-table entry or a CSI condition says so was asked of `garamsh/gitops` on 2026-08-24 and has not been answered. If a write is the only signal there is, that is a finding to record rather than a gap to close, and it decides what the controller could ever check.
- **Resizing an agent's volume.** A StatefulSet's claim template is immutable after creation, so a change to `spec.storageSize` on an existing `Agent` cannot be satisfied by editing the workload. The agent's memory can now move to a larger claim (ADR 0065), and the workspace's claim still cannot. ADR 0005 accepts the limitation without answering it. The controller leaves the claim as it is and says so on the object, which makes the limitation visible without answering it either.
- **Who reclaims the volume of an agent GRN that no longer exists.** The volume is kept so that a re-created `Agent` can rebind it, and nothing here can tell a volume no `Agent` will ever rebind from one that one will: this operator deletes nothing but the StatefulSet of a deleting `Agent` (ADR 0042), whose claim template's claims the deletion does not reach, and learns of no agent's end. A GRN does not come back once its definition is gone, so such a volume accrues once per agent that ends; issue #152 records three on the `gitops` cluster on 2026-09-06, none bound and none owned. What would settle it is a route that says a definition is gone, or a deployer who has to reclaim one.
- **What `workspace` means as a value key, if it is ever one.** The word names three things: a project GRN in `garam`'s `AgentValues` example (`garam@8f9dd9d:api/openapi.yaml:1606`); the place an agent's actions run and its capabilities are enforced, in `garam`'s ADR-0012 (`garam@8f9dd9d:docs/architecture/adr/0012-agent-operator-model.md:31,67`) and in the second container ADR 0023 builds here; and, in ADR 0007, a composition value `garam` would hand this operator. Nothing reads a key of that name. Nothing here settles which, if any, a definition's `workspace` key would mean; what would is a key this operator is asked to read, with `garam` stating what its value names.
