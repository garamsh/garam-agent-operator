# Integration

How a change reaches `dev` and then `main`, and which checks run at each step.

## Current decisions

- **One entry point carries every check, and CI invokes it by name.** `make ci` is module tidiness (`go mod tidy -diff`, which changes nothing), the lint configuration, lint, format, test, build, a check that the image build context holds every file Go source embeds, and the action pins. `.github/workflows/checks.yml` runs it as a single `make` invocation. The workflow spells out no command inside a target and holds no tool version the `Makefile` does not.
- **The end-to-end suites run on no workflow.** `make test-e2e-control` runs the control service's suite (the built binary against a PostgreSQL container and a real garam at `GARAM_REVISION`, whose files `make garam-e2e` copies out of garam's test image pinned by digest), and `make pair-run` runs the gaon operator against that garam and the control service. No workflow invokes either: `.github/workflows/test-e2e.yml` ran the manager's Kind suite and the control suite together, and [ADR 0083](adr/0083-remove-the-kubernetes-manager.md) deleted it with the manager. Putting them back in CI needs a workflow that logs in to ECR for garam's test image, which is open below.
- **Nothing runs on `dev`.** No workflow fires for a push to `dev` or for a pull request into it. The one workflow that checks runs on a pull request into `main`, which is the promotion below, and on nothing else.

| Workflow | Runs on | Why there |
|---|---|---|
| `Checks` | `pull_request` with base `main` | The promotion is where a batch of `dev` is checked before it becomes released state. |
| `release` | `push` of a `v*` tag | Publishes a release (`delivery.md`, ADR 0051). It checks nothing: what it builds is a commit the promotion already checked. |

- **No `push` trigger remains.** The promotion is merged by fast-forward and `main` moves only by a promotion, so `main` lands on the commit the pull-request run already checked. A run on the `push` to `main` would check that tree twice for one promotion.
- **The author's local run is the only gate before `dev`.** A contributor runs `make ci`, `make test-e2e-control` and `make pair-run` before pushing, which `README.md` states where the commands are. A pull request into `dev` carries no check suite, so a reviewer relies on the run the author reports in the pull request's Verification field, and nothing on the forge ties that report to the head commit.
- **A green run means the promotion passed.** It is reported on the promotion pull request, against the batch it carries. A break a merge brings to `dev` is not reported on `dev`: it is found by a later contributor's local run, or at the promotion.
- **The check workflow's credential cannot write.** It sets `permissions: {}` at the top and grants `contents: read` on its one job. A step that needs a write grant takes it on the job that needs it and nowhere higher. No workflow here assumes the pull role `arn:aws:iam::486152169996:role/github-actions-garam-agent-operator-pull` or runs in the `promotion-e2e` environment any longer: the role and the environment belong to `garamsh/aurora` and `garamsh/infra` and are unused by this repository until an e2e workflow returns, and removing them is theirs to decide. The release workflow sets `permissions: read-all` and grants its one job `contents: read` and `id-token: write`, the federated credential it pushes with.
- **`main` advances only by a human promotion**, a pull request from `dev` to `main` merged by fast-forward (`git.md` §PRs, ADR 0070). A squash, a rebase or a merge commit leaves `main` holding a commit `dev` never held, so `main` diverges from `dev`, and a squash or a rebase also stops the commits that a release tag and a development image's hash tag name from resolving on the branch holding released state. After every promotion, `git merge-base --is-ancestor origin/main origin/dev` succeeds.
  - **Measured on 2026-10-22: `origin/main` and `origin/dev` are both `f3841de`.** Three promotions have carried a batch to `main` — #384, #386 and #390 — and three releases were cut from it, `v0.1.0-dev.1` at `d6a7e76`, `v0.1.0-dev.2` at `dbe85d4` and `v0.1.0-dev.3` at `f3841de`, named `v0.1.0`, `v0.2.0` and `v0.3.0` when cut and renamed under ADR 0081. The divergence `main` once carried is closed, and the check above holds.
- **A release is a `v0.1.0-dev.N`, `v0.1.0-rc.N` or `v0.1.0` tag placed on `main`'s tip after a promotion** (ADR 0051, ADR 0081). The person who promoted tags the commit the promotion left on `main` and pushes the tag, and the release workflow publishes it. Not every promotion is released. A tag on a commit only `dev` holds is refused by the workflow, before any credential.
- **A promotion pull request is opened when the promotion is performed, and merged then.** It is not held open while `dev` moves: its head is `dev`, so every merge into `dev` would update it and fire the workflow, one run per merge again.
- **The GitHub default branch is `dev`.** That is a repository setting rather than anything in these files, so what follows is what this repository requires of it, not a description of what it holds. Two things rest on it: a pull request opened from the forge targets `dev` without the author choosing, which is what `git.md` §Branches requires of every task; and GitHub reads `.github/dependabot.yml` from it, so the pin-bumping bot that `ci.md` §Verify a pinned dependency requires a pinned dependency to name runs only once the setting is `dev`.
- **Dependabot opens version updates against `dev` for three ecosystems, as `.github/dependabot.yml` declares them.** They are the workflows' actions (`github-actions`), the base images in the Dockerfile under `/build` (`docker`), and the Go modules in `go.mod` (`gomod`). Two groups of modules move in one pull request each: `k8s.io/api` and `k8s.io/apimachinery`, which share types, and the two testcontainers-go modules, which are tagged at the same commit. Every other module moves on its own: each is released independently, so a lone bump keeps a break with the module that brought it. No ecosystem reads a `Makefile` variable or a reference inside Go source (`docker` reads the files in the directory an entry names whose name matches `dockerfile` or `containerfile`, at `dependabot-core@0db0342:docker/lib/dependabot/docker/file_fetcher.rb:12,25-28,58-61` and `file_parser.rb:84,93-94,125-126`), so the PM moves those pins, and each says so where it sits. golangci-lint's version in the `Makefile` is reviewed when a Go release or a lint failure requires it. The PostgreSQL image in `tests/control/main_test.go`, a testcontainers argument, is reviewed at each promotion to `main`.
- **Nothing here enforces any of it.** No branch is protected, no check is required to merge, and the workflow is not named as a gate. The triggers decide what runs, not what must pass.

## Rationale

Which events fire the workflow is [ADR 0028](adr/0028-run-the-checks-and-the-e2e-suite-on-the-promotion-to-main-and-nothing-on-dev.md), whose end-to-end half [ADR 0083](adr/0083-remove-the-kubernetes-manager.md) supersedes with the workflow it ran. It applies the owner's direction that work lands on `dev` without CI and `main` is promoted in batches (issue #175), after five merges into `dev` on 2026-09-25 produced fifteen runs. Leaving the gate before `dev` to the author's local run rests on #108 and #113, which together made the end-to-end suite a command a contributor can run against a cluster the run owns; the commands are `make test-e2e-control` and `make pair-run` now.

What advances `main` is [ADR 0015](adr/0015-run-the-e2e-suite-where-a-change-lands-and-advance-main-only-by-a-human-promotion.md), settled on issue #115. Its trigger decisions are superseded by ADR 0028, and its publishing as what advances `main` by [ADR 0051](adr/0051-publish-a-release-from-a-version-tag-on-main-through-a-release-workflow.md), which makes a release a version tag on `main` placed after a promotion, in the form ADR 0081 decides. Its promotion stands. Its merge without squashing is superseded by [ADR 0070](adr/0070-promote-dev-to-main-by-fast-forward.md): the promotions merged that way, #191, #198 and #269, left `main` holding three merge commits `dev` never held, so a promotion is now a fast-forward, and `main` is reset once to `7c216469476d`, which holds the old tip's tree, before the next one (#335).

That `main` is released state and `dev` is where work integrates is [ADR 0002](adr/0002-dev-integration-branch.md), which named the promotion as an explicit act nothing described. ADR 0015 describes it. That the promotion cannot squash also follows from [ADR 0014](adr/0014-the-image-repository-is-immutable-and-a-deployment-references-a-digest.md), which fixes an image tag as a commit's abbreviated hash so a reader of a deployed reference can run `git show` on it.

## Open questions

- **Whether a break on `dev` goes unnoticed for too long.** No run observes `dev`, so a merge that breaks the checks reaches the branch every task branches from and is found by whoever runs the suite next. Nothing has yet measured how long that takes here or what it costs; a break found late enough to cost more than the runs saved is the evidence that reopens ADR 0028.
- **Whether the end-to-end suites return to CI.** No workflow runs `make test-e2e-control` or `make pair-run`, so a break in the control API against a real garam is found by the author's local run or not at all. Restoring a workflow needs an ECR pull role for garam's test image, which is `garamsh/aurora`'s, and a decision whether it runs on the promotion as `test-e2e.yml` did.
- **Whether `main` should be protected.** Never pushing to `main` is held by discipline: `git.md` §Branches states it, and `gh api .../branches/main/protection` returned 404 on 2026-09-01 and again on 2026-10-22. It becomes load-bearing once `dev` is the default and `main` means released state. Issue #115 recorded it rather than changing it, because requiring review blocks every merge while one account holds both roles.
