# ADR 0023: Run an agent's workspace as a second container this operator names, and give it the user the Pod already names

> Status: accepted
> Date: 2026-09-06

Append-only: once merged, the body below is not rewritten. A fact later found wrong is corrected in an appended note, not edited out; a revised decision is a new ADR that supersedes this one.

## Context

No agent this operator constructs can read a file or run a command, and the reason is that the workload carries no process that could. `internal/controller/agent_statefulset.go` built two container names before this change: `agentContainerName` and the `credentialsContainerName` init container. `gagent`'s ADR 0017 describes one Pod with two containers, and the second is the workspace: the process that serves Read, Write, List and Exec over gRPC, which the agent's `files` and `shell_exec` tools call into. So an agent starts, loads its tool tree, reports `Available=True`, and fails those two tools on a connection error — the third state this repository has met that reads green over a question nobody asked, after issue #72 and the premise below.

**Why it was never asked for.** `workspace` already means the other thing in these documents: a key of a definition's `values` ([ADR 0007](0007-claim-definitions-from-a-poller.md)), one of the things `garam` composes (`agent.md` §Current decisions). By the division those same lines draw — composition is `garam`'s, construction is this operator's: the image, the storage size, the security context, the scheduling — a container is unambiguously construction. The division was never wrong. The matching word is why nobody went to look, and `agent.md` §Open questions recorded the absence as an unknown rather than as a choice.

**Issue #153 was opened on a premise that is false, and it is recorded here because the rejected options rest on it.** It carried, received through `gitops#3` rather than read at a commit, that the workspace must run as root with `SYS_ADMIN` because each exec unshares a network namespace. `gagent@9b0e399:internal/workspace/shell/process_linux.go:174-198` branches on the effective uid: root takes `CLONE_NEWNET` and needs the capability, and non-root takes `CLONE_NEWUSER | CLONE_NEWNET` with the uid mapped to itself, which is creatable without privilege. Isolation is kept either way, and it is per call — `NoNetwork` is a field on `ExecRequest`, not a property of every exec. No capability is owed, so neither a namespace split nor a relaxed PodSecurity level is.

**It fails closed rather than open.** `gagent@9b0e399:internal/workspace/shell/process_linux.go:131` refuses every exec with `ErrAgentUIDUnavailable` where the process is neither root nor the configured account. There is no path that runs unisolated while believing it is isolated.

**The two uids do not agree by themselves, and the disagreement refuses every exec.** `exec-uid` defaults to 1001 (`gagent@9b0e399:internal/config/workspace.go:19`), the account `build/workspace.Dockerfile:39` creates, and the flag's own text says it must equal the workspace's own uid for single-account mode (`:32`). [ADR 0010](0010-copy-an-agents-credential-into-a-memory-volume-the-pods-own-user-owns.md) names 65532 at Pod level, which every container inherits unless it overrides. A workspace container added without deciding this runs as 65532 with `exec-uid` at 1001, and `:131` above refuses every exec.

**The image cannot be the agent's, and one exists.** `gagent@9b0e399:build/agent.Dockerfile` is distroless and carries no shell, and Exec children are `sh -c`, which is why `build/workspace.Dockerfile:29` is `debian:13-slim`. Read from the ECR repository `garam/gagent-workspace` in account `486152169996`, region `ap-northeast-2`, on 2026-09-06: tag `0.1.0` at `sha256:ce3256dcd5ac46ceaa9d5e445da69998728b123f86bca92b4001185cfa0e6a7e`, pushed 2026-09-03, an OCI image manifest and **not an index**, `linux/amd64`, labelled with revision `b61451e6e0de188e8e373fdb74c43abaca5a31f0`. Its config declares `Entrypoint ["/gagent"]`, `Cmd ["workspace"]`, `User root`, and **no `WorkingDir`**.

**The image's default workspace directory is unwritable by the user this Pod names, and the failure is at startup rather than at the first call.** The workspace opens its directory before it listens — `gagent@9b0e399:internal/workspace/server/serve.go:54` calls `files.Open`, which is `os.MkdirAll` on the absolute form of the configured path (`internal/workspace/files/files.go:52-58`). The configured default is the relative `data/workspace` (`internal/config/workspace.go:14`), and with no `WorkingDir` in the image that resolves to `/data/workspace`. The layer carrying `/data` in the image above was read directly from the registry on 2026-09-06 and the entry is `drwxr-xr-x 0/0` — root-owned, mode 0755, no group write. At uid 65532 `MkdirAll` returns `EACCES`, `Serve` returns the error, and the container exits. So the directory is not a setting this decision could have left alone.

**What that directory has to be instead is the one question here that was not already answered.** The Pod carries a volume the agent's state is claimed on ([ADR 0005](0005-statefulset-of-one.md)), mounted into the agent's container at `/var/lib/gagent`, and the comment on `toolsMountPath` in `agent_statefulset.go` records that path as one the agent writes. Putting the workspace there is a second process on a volume the agent already holds, which is a larger claim than giving an unused volume a user, and it is argued as one below. What makes it available at all is measured and already recorded — the bullet in `agent.md` §Current decisions on the Pod's supplementary group: on 2026-08-24, on a volume a `csi.proxmox.sinextra.dev` StorageClass provisioned — the mounted directory came up root-owned at mode 2775 carrying the Pod's group, and a container whose uid is neither root nor that gid wrote to it. The Pod's `fsGroup` is what the image's `/data` does not have.

## Decision

**An agent's Pod carries a second container, `workspace`, running an image this operator's configuration names.** A new flag, `--agent-workspace-image`, names it, in the shape [ADR 0019](0019-mount-an-agents-tool-tree-from-an-image-this-operator-names.md) gave `--agent-tools-image` and ADR 0010 gave `--agent-copy-image`: an image the workload carries that no `Agent` names, coming from the deployer rather than from a definition.

**The flag has no default and unset builds the workload this operator built before a workspace could be named.** No container, nothing written on the agent, and the whole of the feature unconstructed — the shape `--agent-tools-image` and `--garam-address` already use. `spec.image` and `--agent-storage-size` refuse a default on the ground that the field asks rather than invents, and a reference to somebody else's registry invented here would be the same defect one layer out.

**Both ends of the link are written, and neither is left to a default.** The workspace is told `GAGENT_ADDR` and the agent is told `GAGENT_WORKSPACE_ADDR`, both `127.0.0.1:8081`. The two images already default to that number (`gagent@9b0e399:internal/config/config.go:34`), so this changes no behaviour today; what it changes is who owns the agreement. Two defaults agreeing is not one number chosen, and nothing in this repository would notice either image moving its own — the failure that produces is a dial to a closed port, reported one call later. It is loopback, which is the only bind `gagent`'s listener accepts while it carries no authentication, and it is inside one Pod's network namespace, so no volume, no socket and no shared mount are involved in the link.

**The workspace is told to run exec children as 65532, the user the Pod already names, and no container overrides that user.** The two numbers have to be equal for the single-account path, and this is the direction the equality is made in. 65532 is a number this operator chose with a recorded reason and 1001 is one the image chose: ADR 0010 decides that the Pod names one user and every container runs as it, because the credential's copy has one owner and every process that reads it must have that owner — a ground that reaches any container added afterwards, and one no image can be asked to answer. Overriding the workspace to 1001 would contradict a decision in force and need an ADR superseding it; stating `GAGENT_EXEC_UID` contradicts nothing. The 1001 account is machinery for the privileged mode this Pod does not run: at a non-root euid `gagent` sets no `Credential` at all and the child inherits the workspace's own account (`gagent@9b0e399:internal/workspace/shell/process_linux.go:174-182`).

**The workspace serves a subtree of the state volume, at `/var/lib/gagent/workspace`.** The volume is mounted into the workspace's container at the path the agent already has it, and the subtree is named in a constant beside that path. It is absolute and this operator's for the reason ADR 0019 gives for `/opt/gagent/tools` — a relative default resolves against a working directory in somebody else's image — and for the second reason the Context measures: the directory that default names cannot be created by this Pod's user.

**The two processes are kept to disjoint subtrees, and nothing but those two constants keeps them apart.** ADR 0005 pins the replica count at 1 because two agent processes against one volume is corruption rather than a degraded mode, and that is one storage engine with two writers. This adds no replica and no second writer to any file: it adds a second process writing a different subtree of one filesystem. The disjointness is the property the decision rests on, and it is enforced by nothing except `stateMountPath` and the path built from it — which is checkable by a reader and is written here so that a later change collapsing the two is caught as the change it is.

**The workspace is given no credential and no tool tree.** ADR 0006's consequence is that any container mounting the credentials volume can read it, and which containers mount it is this operator's decision; the workspace reads no credential. The tool tree stays the agent's alone: tools live in the agent and reach the workspace over gRPC, and the workspace hosts none (`gagent@9b0e399:build/workspace.Dockerfile:20-23`).

**It carries the same container security context as the other two and pulls at every start.** `allowPrivilegeEscalation: false` and every capability dropped, which is what the unprivileged exec path needs and no more; and `PullAlways`, on the ground the agent's image already carries — it is `gagent`'s image, and that project requires a consumer to pull always. It carries no resource requests: `spec.resources` says in its own doc comment that it is the agent container's, and a second container is not what a person writing that field is sizing.

**No `Agent` names any of this and no field is added.** The image, the address, the user and the directory are all construction, and `v1alpha1` is untouched.

## Consequences

Easier: an agent this operator constructs has something to dial, so `files` and `shell_exec` can do what they are registered for. That is the whole of what this buys and it has not been shown in a cluster — see below.

**`spec.storageSize` now sizes one volume for two consumers.** An agent's files and its state compete for the same quantity, and ADR 0005 already records that the claim template is immutable after creation, so an agent that fills its volume with files cannot be given a larger one. That is a real cost of putting the workspace on the state volume and it is accepted here rather than solved.

**Every agent's Pod now pulls a third image**, and a node that cannot pull it leaves the Pod short of a container it needs. That is the same price ADR 0010 accepted for the copy image, met a second time.

**A deployment that does not set the flag is no worse off than it is today, and no better.** Unset was chosen over required because requiring it would refuse to start every deployment now running, over a value no overlay yet carries. What that gives up is the notice: ADR 0019 could leave `--agent-tools-image` optional on the ground that an agent finding no tree refuses to start and says the rest itself, and **that ground does not hold here** — an agent with no workspace starts, binds its port, and reports `Available=True`. The manager's startup line naming the consequence is therefore the whole of the notice rather than the first half of one, and the gap it leaves is `agent.md`'s standing one: `Available` is read off ready replicas and a container that cannot do its job is ready on those terms like any other.

**Nothing here has been exercised against a cluster.** What is verified is what this operator builds and what a `restricted` namespace admits, at the integration layer against the Kubernetes 1.36.2 API server — including that the Pod carrying the workspace is admitted, and that the same Pod carrying `SYS_ADMIN` on that container is refused, which is the control saying the standard is enforced there. envtest has no kubelet, so no layer in this repository starts the container, dials the port, or runs an exec. The e2e suite is not extended: it runs a substitute image that serves no workspace contract.

**Two things about the unprivileged exec path are received rather than measured here, and both would present as a refused exec rather than as a broken Pod.** `CLONE_NEWUSER` needs unprivileged user namespaces enabled on the node, which `gagent` refuses explicitly where they are not; and whether the `RuntimeDefault` seccomp profile this Pod names permits that clone is not something any layer here can answer. Both bound the isolated subset of execs — a call that does not ask for `NoNetwork` reaches neither — and both are recorded in `agent.md` §Open questions rather than asserted.

**The reference an overlay sets pins one architecture.** The published workspace image is a single OCI manifest and not an index, so `configuration.md`'s rule applies to it: the platform manifest's digest is taken and the architecture is recorded rather than left implicit. It is `linux/amd64`, and a node of another architecture fails to pull rather than mismatching silently.

**This operator now says what an agent may do to a filesystem as well as which tools it has.** ADR 0019 made the tool set the deployer's; the workspace image is the process behind `files` and `shell_exec`, so which build of it a cluster runs decides how those behave. Nothing here reads what is inside that image, exactly as nothing reads what is inside the tool tree.

ADR 0019's shape is extended and nothing is superseded. [ADR 0009](0009-construct-a-claimed-agent-from-the-operators-own-configuration.md) decided that what a definition does not name comes from this operator's own configuration, and every ADR adding an image since — ADR 0010's copy image, ADR 0019's tool tree — has extended it rather than replaced it; this is the fourth image on the same road. ADR 0005 is untouched: replicas stay 1. ADR 0010 is untouched and is the reason the uid is 65532.

## Rejected alternatives

**Running the workspace as uid 1001 by overriding the container's user.** It makes the two numbers equal from the other end and it contradicts ADR 0010's decision that the Pod names one user and every container runs as it — which would need an ADR superseding it, for a number chosen by an image's `useradd` rather than by anyone who can see this Pod. It would also leave the workspace unable to write the state volume, whose group is the Pod's.

**Adding `SYS_ADMIN`, splitting the namespace, or relaxing PodSecurity to `privileged`** — the three options issue #153 was opened with, all withdrawn. Each pays for a capability the Context shows is not owed at a non-root euid.

**An `emptyDir` for the workspace directory.** It is container-local and needs no argument about sharing, and it hands an agent a workspace erased at every restart — inside a StatefulSet whose entire ground (ADR 0005) is a durable single-writer store. That is a shape contradicting itself, and the honesty of the smaller diff does not pay for it.

**A second `volumeClaimTemplate` for the workspace.** It separates the two subtrees at the storage layer rather than by a constant, and it is not available to an agent that already exists: ADR 0005 records that a claim template is immutable after creation, so this would be a shape only new agents could take. What would revisit it is an agent whose files and state genuinely need separate sizes.

**Leaving the workspace directory at the image's default.** Measured above: it resolves to a root-owned `/data` this Pod's user cannot create in, so the container never listens. There is no version of this decision that does not name the directory.

**Requiring the flag.** It would refuse to start every deployment running today, over a value no overlay yet carries — ADR 0019's ground, which still holds even though the image, unlike the tool tree's, exists. What it costs is stated in §Consequences rather than hidden: the notice is one log line.

**Overriding the container's `command` or `args`** to pass `--addr`, `--workspace` and `--exec-uid`. It would make this operator the author of another project's argument list and take `ENTRYPOINT` and `CMD` away from the image, which is ADR 0019's rejection and holds here for the same reason. Every one of these settings resolves from the environment under `GAGENT_<KEY>` (`gagent@9b0e399:internal/config/config.go:276-277`), which takes nothing from the image.

**Giving the workspace the credential or the tool tree.** Neither is read by it, and each mount is one more reader of something that has readers for a reason.
