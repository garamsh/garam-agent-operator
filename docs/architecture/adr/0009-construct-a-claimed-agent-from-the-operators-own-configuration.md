# ADR 0009: Construct a claimed agent from the operator's own configuration, and place the credential the claim admits it to

> Status: accepted
> Date: 2026-08-26

Append-only: once merged, the body below is not rewritten. A fact later found wrong is corrected in an appended note, not edited out; a revised decision is a new ADR that supersedes this one.

## Context

[ADR 0007](0007-claim-definitions-from-a-poller.md) left the poller claiming definitions and constructing nothing, and named the reason: `AgentSpec` requires an image and a storage size that no definition carries. Measured against the type rather than recalled, it requires a third — `credentialsSecretName`, naming a Secret nobody in this repository creates. Those are issues #75 and #79, and they are one change: both stand between a claimed definition and a constructed `Agent`, both are the poller's, and either taken alone lands a construction path the other rewrites.

**The division is not reopened here.** ADR 0007 decided that a definition says what an agent is and this operator says how one is built, and `garam`'s own side has since given the reason a name rather than re-deciding it: `garam` has never seen this cluster's nodes, its registry, its storage classes or its quotas, so a definition carrying an image would be `garam` asserting something about an infrastructure it cannot observe. The free-form `AgentValues` map makes the wrong answer easy and legal — nothing in `garam` would reject an `image` key and nothing here would notice — which is why the prohibition is restated as a rule this operator keeps rather than left to follow from the division.

**`garam`'s half of the credential is built, and its schema decides most of the design.** `garam@5130ca9:api/machine.yaml:445-485` defines `MachineCertificate` with six required fields — `grn`, `certificatePem`, `privateKeyPem`, `issuerPem`, `serverRootPem`, `notAfter` — and three sentences that bind what is built against it: `garam` stores no private key, so one is returned once and a holder that loses it asks for another certificate; `issuerPem` is the authority that signed the certificate and **is not what `garam` is verified against**, because the two directions rest on different roots (`garam`'s ADR-0040); and one shape serves both routes that issue a certificate, which differ in who may ask rather than in what comes back. The route is `POST /agents/{agent}/certificate` — `issueAgentCertificate` — and not `/identity/certificate`, which renews the caller's own identity and names no subject.

**The mechanism was measured before it was built.** On `garam-dev` on 2026-08-25 from 17:00 UTC, against the machine listener running `garam-server-dev@sha256:133ba5629242621a9b50b68021aa01124e492ebb321a302035aff6a474b5b85e` — the image built at `garam@1150b88` — with an operator certificate minted for the purpose:

- The route answers 201 with all six fields. The leaf carries the agent's GRN in a SAN URI and lives about a day with jitter, so two issued together do not expire together.
- `serverRootPem` is byte-identical to the root the cluster hands the listener, `CN=garam machine server root`, `CA:TRUE`, five years. `issuerPem` is `CN=grn:root:default:org:garam`, `CA:TRUE` `pathlen:0`, ten years. **Pinning `issuerPem` does not reach `garam` at all**: no HTTP response, `unable to get local issuer certificate`, beside a 200 from the same client pinning `serverRootPem`. The two are not interchangeable and the wrong one fails at the handshake rather than at a request.
- **An operator may ask again at any time.** Two calls seconds apart answered 201 and 201, with a different certificate and a different key. There is no window and no `already_exists`: the fence `garam` puts on an operator renewing its *own* identity — 409 `failed_precondition`, "certificate is not yet within its renewal window", measured on the same listener in the same session — has no counterpart here.
- **An agent renews its own certificate on the same route**, over the connection that certificate authenticated, and a certificate already superseded by a later one still renews. That is `garam`'s ADR-0040 §6 and `garam@5130ca9:internal/agent/service.go:93-99`; an agent's certificate is refused on `/definitions` as "caller is not an operator" and on another agent's certificate route.
- **A 403 cannot be branched on.** An agent assigned to another operator, an agent that does not exist, and an agent this operator has been replaced on all answer 403 `permission_denied`, "agent is not assigned to this operator" — deliberately, so that a caller learns nothing about the agents it does not hold (`garam@5130ca9:internal/agent/agent.go:50-54`).
- **A claim reported in `/definitions` is not proof this operator holds the agent.** After the assignment was moved to another operator, `/definitions` went on listing the definition to the *replaced* operator and reported `claim.epoch` as the epoch of the operator that replaced it; a second claim answered 409 `already_exists`; the certificate route answered 403. The read is scoped by the definition's operator field and the claim is joined in from the assignment whoever holds it — `garam@5130ca9:internal/agent/queries.sql:71-76` — so the two say different things and only the second is the epoch.

## Decision

**The image and the storage size are flags on the manager, and there is one of each for every agent this operator constructs.** `--agent-image` and `--agent-storage-size`, neither with a default. That puts the choice with the operator's deployer, which is the audience ADR 0007 says `image` asks, and it is the cheapest thing that unblocks a claim constructing an `Agent`. A ConfigMap, and a kind above `Agent` naming a class of them, are the same audience at more cost, and nothing yet needs more than one answer: `garam` holds two agents for this operator and two is not a fleet. `simplicity.md` §A division is a response is what refuses the kind until a second case arrives, and what would settle it is a second agent needing a different image or a person who is not the deployer needing to choose one. **No value of a definition names either, and none is read.**

**Neither flag has a default and both are required where `--garam-address` is set.** `api/v1alpha1/agent_types.go`'s recorded reason for `image` — the field asks rather than invents — holds one layer up, and a storage size invented here would be the same defect in a field a person cannot see. An operator that claims agents it has no way to build is a worse state than one that refuses to start, so the manager refuses. ADR 0007's default is untouched: `--garam-address` unset leaves this operator making no outbound call and asking for nothing.

**Construction is driven by every definition this operator holds a claim on, not by the pass that claimed one.** `garam` reports a claim for as long as the definition exists, so a poller that built only on a fresh claim would build nothing after a restart and nothing for a definition claimed by an earlier release.

**The certificate is asked for only where what comes back can be stored at once, and the store is what makes it obtained.** `garam` generates a private key per certificate and keeps none, so a credential that reaches no store is gone. Two rules follow and both are load bearing. Nothing asks for a certificate it has somewhere to put already: the poller reads whether the Secret exists and stops there when it does, because a certificate asked for with nowhere to go is key material created and dropped. And **a failed write is answered by another certificate, never by retrying the write** — a credential held in this process to be retried is one only this process has, and it goes with the process. This inverts the usual shape: the durable step is not the call, it is the store.

**What is read to answer "is it placed" is the Secret that holds the key, and never the `Agent` beside it.** The `Agent` is created first so that the Secret is owned by it, so a refused placement leaves an `Agent` standing with no key anywhere. Read as constructed, that credential would be lost with nothing left to ask again.

**The Secret carries four keys and the issuer is not the server root.** `certificate.pem`, `key.pem`, `issuer.pem` and `server-root.pem` — the three names `garam`'s own mint writes an identity's files under (`garam@5130ca9:internal/cli/issue_certificate.go:113-115`), with the root that arrives beside them named for what it is. `serverRootPem` is what a holder verifies `garam` by; `issuerPem` is carried because it is the chain the agent presents, and it is under its own name because an agent that pinned it could not reach `garam` at all. `notAfter` is logged and not stored: `garam` answers it so that nothing parses a PEM, and no reader here has anything to do with it.

**This operator places an agent's first credential and replaces none.** An agent renews its own over the connection that credential authenticated, which is `garam`'s decision and is measured above, and this operator's route is what recovers one that expired. So a Secret that exists is left alone, and re-placing one is deleting it. Nothing here schedules a replacement, because a second placement would overwrite a credential the agent may already have renewed past.

**A 403 is "not mine right now" and construction stops there.** Nothing is retried and nothing is branched on, because the three states `garam` answers it for are not distinguishable and only one of them would be worth a different response. The next read of the definitions is the whole of the reply.

**The epoch is met at the certificate route and nowhere else.** A claim in `/definitions` reports whichever assignment exists, so it survives a reassignment and says nothing about who holds the agent; the certificate route compares the assignment's operator with the caller and is therefore the fence. This operator does not poll for its own dispossession: a Secret that exists means no call is made, so what it learns is that it was replaced the next time it needs a credential. Tearing a running workload down on that would be worse than leaving it — the credential in the Pod is the agent's to renew, and `garam` publishes nothing that says an operator should stop.

**An `Agent`'s name is the digest of the whole GRN, and this operator names the Secret after it.** `agent-` and sixteen hex characters of the SHA-256 of the GRN, with `-credentials` appended for the Secret. The name reads no part of the GRN: what a GRN's segments mean is `garam`'s, and a name cut out of one moves when that format does, orphaning every object already built under the old shape. Deterministic, so the `Agent` for a definition is found by name rather than by a label; and short enough that the `Agent`'s 52-character bound holds with the suffix.

**The GRN it was constructed from is reported in `AgentStatus`**, which is the field ADR 0007 said would arrive with the change that first fills it. It is not in the spec: a GRN `garam` minted is not something a user writes.

**Constructed agents are built in the manager's own namespace**, the one `POD_NAMESPACE` already names for this operator's own credential. It is what keeps the power this change adds as small as it can be: `create` on Secrets is granted in one namespace rather than across the cluster, and `create` on `Agent` with it.

## Consequences

Easier: the path from `garam`'s console to a running workload is closed. A definition is claimed, an `Agent` is constructed, its credential is placed, and the reconciler that has been building StatefulSets since 2026-08-24 does the rest — with the Secret's arrival waking it, which is the mechanism it already had for an `Agent` a person wrote.

Harder, and this is what the decision gives up: **an agent's private key reaches etcd**, where before this operator wrote none. It is the same class ADR 0008 accepted for the operator's own credential and it is now one Secret per agent. The grant that carries it is `create` and not `update`, in one namespace, which is the smallest shape that places a credential at all.

**A deployment that sets `--garam-address` and neither agent flag no longer starts.** That is deliberate and it is a change in behaviour, not only an addition: an operator that claims agents it cannot build holds them away from an operator that could.

**Two agents reach every `Agent` a definition constructs and neither is this repository's to fix.** `garam`'s adapter is what reads an agent's client credential, in a sidecar in the agent's pod (`garam@5130ca9:docs/architecture/adapter.md:28-31`), and it reads the private key under the owner-only rule every `garam` process reads key material under — refusing a file any group can reach and one owned by another user (`garam@5130ca9:internal/keyfile/keyfile.go:30-41`). The volume this operator mounts is `0440` and root-owned, which is the tightest a Secret volume the kubelet writes delivers while the Pod carries a group, and ADR 0006 measured that the group is what makes it readable at all. So the reader `agent.md` recorded as not subject to that rule — `gagent` — was the wrong reader, and the constraint is real for the credential this change places. The workload also carries no adapter container. Both are recorded in `agent.md` §Open questions with what was measured, and neither is answered here: the remedy is not this operator's alone, which is what that open question already says.

**Nothing renews an agent's credential from this side, and what happens if an agent lets its own expire is untested here.** The remedy exists and is cheap — the operator's route is unfenced and answers again at any time — but whether `gagent` and the adapter beside it renew, and what either does when the file changes under them, is their behaviour and is not measured in this repository. Building a replacement loop against an unmeasured reader would duplicate a renewal `garam` already decided is the agent's.

**A pass that fails to place a credential costs a certificate.** The next pass asks for another rather than retrying the write, so a namespace that refuses the write mints and drops one certificate per interval until it stops. That is the price of never holding key material only in memory, and it is bounded by the poll interval and visible in the log.

Ruled out: **reading the image out of a definition's `values`**, in every form. It would work, it would pass every test here, and it would move a decision about what this operator runs as a workload into a field a console user edits — for a cluster that user cannot see. Per-agent configurability, if it is ever wanted, is a schema change with an ADR of its own and not a convention about a map key.

Ruled out with it: **a kind above `Agent` naming a class of them**, which serves a heterogeneous fleet that does not exist and costs a kind to do it. **Naming an `Agent` after a segment of its GRN**, which reads inside an identifier this repository holds and does not interpret, and rebuilds every name if `garam`'s format moves. **Replacing a credential this operator already placed**, which would overwrite what an agent renewed for itself and put two writers on one Secret — ADR 0008's rule that a copy step is safe exactly when the copy's source is the only writer, met one level down. **Branching on a 403**, which invents a distinction `garam` deliberately refuses to make. And **tearing down a workload whose agent was reassigned**, which acts on a signal this operator only receives by chance and destroys state on it.

Not decided here: **where a constructed agent runs, beyond the operator's own namespace.** One namespace is what the first deployment needs and what keeps the grant smallest; a second that needs another is what would decide it. Not decided here either: **what this operator reports back to `garam`** about an agent it has now actually built, which `agent.md` already carries as an open question and which this change gives its first real subject.
