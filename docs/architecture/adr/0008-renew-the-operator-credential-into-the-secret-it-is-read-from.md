# ADR 0008: Renew the operator's credential into the Secret it is read from

> Status: accepted
> Date: 2026-08-25

Append-only: once merged, the body below is not rewritten. A fact later found wrong is corrected in an appended note, not edited out; a revised decision is a new ADR that supersedes this one.

## Context

[ADR 0007](0007-claim-definitions-from-a-poller.md) left one question open and this answers it: **what rewrites the certificate this operator authenticates with.** It decided the certificate is read at each handshake through `GetClientCertificate`, and recorded that re-reading delivers nothing on its own — a file nothing rewrites reads the same until it expires, and that is indistinguishable from working rotation until the day it stops. Nothing on either side could close it then: `garam`'s renewal route was an agent's, and an expired certificate has no connection left to renew over.

`garam`'s #515 closed that side. `garam@1150b88:docs/architecture/adr/0046-an-operator-renews-its-certificate-by-presenting-the-one-it-holds.md` (`accepted`) decides an operator renews over the connection its current certificate authenticated, on `POST /identity/certificate`; the route names no subject, so there is nothing to authorize past the handshake. Three refusals bound it, and `garam` tells them apart by kind rather than by status: too early is `failed_precondition`, superseded is `already_exists`, expired and "not an operator" are `permission_denied`. The window opens once two thirds of the presented certificate's own validity has passed, measured off that certificate rather than off a configured lifetime (`garam@1150b88:internal/operator/service.go:118-130`), which at their default lifetime is about eight hours wide. `garam` renews the certificate it last issued an operator and no other, so a certificate outside that lineage is refused for good (`garam@1150b88:internal/operator/operator.go:64`).

**That route was merged upstream and undeployed when this was decided, and is deployed now.** Measured on `garam-dev` on 2026-08-25 with a real operator certificate: the machine listener runs the image built at `garam@106aae3`, which predates #515, and `POST /identity/certificate` answers 404 there — the same answer as a path that listener never had, while `POST /agents/{agent}/certificate` answers 403 with an error body, so the 404 is absence rather than refusal. `/agents/{agent}/certificate` is not that route under an older name: it exists at both commits, it issues an *agent's* certificate to the operator that claimed it, and it names a subject an operator cannot be.

**The bump landed while this was being written.** Measured again on 2026-08-26, against `garam-server-dev@sha256:133ba5629242621a9b50b68021aa01124e492ebb321a302035aff6a474b5b85e` — the image built at `garam@1150b88`, carrying the `GARAM_MACHINE_SERVER_ROOT_FILE` the earlier one did not: a freshly minted operator certificate authenticates, and `POST /identity/certificate` answers 409 `failed_precondition`, `certificate is not yet within its renewal window`, while `/identity/nonsense` still answers 404. The control that established the route's absence a day earlier is what establishes its presence now.

Two facts about the manager's own Pod bound what could be built. Measured on `garam-dev` on 2026-08-25, from inside a Pod carrying the manifest this change ships: with no `fsGroup` a Secret volume's files arrive `root:root` and uid 65532 — the uid `Dockerfile:38` runs the manager as — is refused them; with `fsGroup` 65532 the same files arrive `root:65532` at `0440` and are read. The container's `readOnlyRootFilesystem` holds in both, and a Secret volume is read-only besides, so this process writes no file anywhere.

What that last fact was taken to mean, on issue #76, is that a renewed certificate needs a volume the operator can write. It does not. **The credential does not have to be replaced as a file to be replaced.**

## Decision

**The credential lives in one place: a Secret, mounted into the manager's Pod, which the operator reads as files and replaces through the API server.** The Pod carries `fsGroup` 65532 and the volume is mounted at `0440`, which is [ADR 0006](0006-credential-group.md)'s mechanism met one layer up on this operator's own credential — access carried by the group rather than by the user, because the kubelet writes those files as root whatever the container runs as.

**Nothing seeds it, so nothing can re-seed it.** The out-of-band mint places the Secret once and the operator's own renewal is the only other writer. There is no copy step between a delivery and a working file, which is what the question "what guarantees exactly once" was asking about: a guard against a second seeding is not needed where there is no seeding. Re-running `garam`'s mint is the intended recovery and takes the lineage back, and the operator adopts what it places within about a minute with nothing restarted.

**The read path and the write path are deliberately different, and the operator holds no permission to read.** It learns its credential from the mounted file and reaches the API only to write a renewal, so its Role grants `patch` on that one Secret by name and neither `get` nor `list`. A reader meeting a patch with no get is meeting that on purpose.

**Both keys move in one patch.** A handshake reads a certificate and the key it was issued with; the kubelet swaps the whole projected directory at once, so no reader sees one beside the other's.

**A second `Runnable` performs the renewal, beside the poller and not inside it.** The two answer to different clocks — a poll is a minute, a renewal window is hours — and a call one makes to `garam` should not hold the other's up. Added to the manager it joins the leader-election group (`sigs.k8s.io/controller-runtime@v0.24.1:pkg/manager/runnable_group.go:99`), which is what `--leader-elect` in the deployment already gives the poller, and here it is load bearing rather than tidy: `garam` renews the certificate it last issued and refuses every other, so two processes renewing one identity leave the loser holding a certificate it can never renew again. **One identity is held by one process, and leader election is what makes that true.**

**Asking is how the operator learns the window opened.** It does not compute the window: it asks every interval and reads the kind of what comes back. `failed_precondition` is not a failure and the next attempt is the whole of the remedy; `already_exists` is reported as needing a mint out of band; anything else is reported as itself. Nothing here restates `garam`'s fraction, so nothing here can drift from it. The interval is bounded on both sides — far below the window, so a listener unreachable for part of it is still met, and far above the delay between a renewal being stored and the process reading it back, because an attempt made inside that delay presents the certificate it just replaced. An hour sits between the two and is the default.

**An unrenewed certificate fails at the handshake and stops nothing here.** The poll goes on failing against `garam` and saying why, and the renewer says which of the three refusals it met. Stopping the poller would remove the only signal and leave the cause nowhere.

**None of it runs until the deployment asks for it.** `--garam-address` unset leaves this operator making no outbound call, as ADR 0007 decided; `--garam-credential-secret` unset leaves it renewing nothing. The volume is `optional`, so a deployment given no identity still starts.

## Consequences

Easier: `garam`'s out-of-band mint becomes what its ADR-0046 intends — one placement per operator rather than a daily delivery — and this repository states the obligation that goes with it instead of leaving it unstated. A renewal survives everything a Pod does, because what holds it is not on the Pod. Re-placing the Secret is both the bootstrap and the recovery, and it is one act rather than two.

Harder, and this is what the decision gives up: **renewed key material reaches etcd.** The bootstrap certificate arrives as a Secret either way, so this adds no class of secret that was absent; what it adds is that every successor joins it. And **the file is `0440` rather than owner-only** — the tightest a volume the kubelet writes delivers while the Pod carries the group, which ADR 0006 measured and `agent.md` records. Nothing this operator mounts requires owner-only: that rule is `gagent`'s, applied to `gagent`'s own files.

The operator now writes an object in its own namespace, which it did not before. The grant is `patch` on one Secret by name, verified against the identity that holds it: the patch answers 200, the same request against another Secret answers 403, and `get` and `list` of the granted Secret answer 403.

**A renewal this operator fails to store is lost.** `garam` keeps no private key and has already moved the record, so the answer cannot be had again and the certificate it replaced can no longer renew. That is `garam`'s ADR-0046 consequence rather than one this adds, and the recovery is the same command as the bootstrap. It is reported loudly and nothing retries it, because there is nothing left to retry.

**A renewal is written before it is read.** The kubelet carries the change into the volume rather than the process writing it, so for about a minute the handshake still presents the certificate just replaced. That is harmless — a superseded certificate authenticates until it expires, and only its renewal is refused — but it is what the lower bound on the interval exists for.

**The refusal this meets most of the time is confirmed live.** `garam-dev` serves the route as of 2026-08-26, and a certificate outside its window is answered 409 `failed_precondition` — which the decision above treats as the ordinary case and not a failure. So the state this loop is in for two thirds of every certificate's life is measured rather than reasoned about. What is built here is otherwise verified against a stub listener and against `garam`'s specification at `garam@1150b88`. **This operator's own first call is still unmeasured**, because no deployment sets `--garam-address` yet: what that waits on is a deployment rather than `garam`.

Ruled out: **a memory-backed `emptyDir` seeded by a one-shot init container**, which is what issue #76 proposed and what `garam` uses for its own key material. It fails on a fact rather than on taste. Such a volume dies with the Pod sandbox, so a restart re-seeds from the bootstrap Secret; the renewal happens about two thirds of the way through a lifetime, so any restart after the first renewal hands the operator back a certificate `garam` has already superseded — it authenticates until it expires and can never renew again. An image bump, a node drain, an eviction or an OOM each does it. That turns `garam`'s once-per-operator bootstrap back into an unpredictable manual re-mint, which is the obligation their #515 exists to remove, and it is silent for the rest of the certificate's life. It also needs a second image and a copy tool in a Pod that has neither, a guard against re-seeding over a renewal, and two files written one after the other where a handshake can fall between them.

Ruled out with it: **writing a renewal to both a volume and the Secret**, which keeps the tighter mode and buys back durability at the price of two stores that must agree — the disagreement issue #76 warns about, reintroduced to save a file mode nothing requires. **Failing the readiness probe when the certificate cannot be renewed**, which restarts a Pod that a restart cannot fix and removes the operator's own account of why. And **reading `garam`'s renewal fraction into a constant here**, which would let this repository's idea of the window drift from the one `garam` enforces.

Not decided here: **what rewrites `--garam-trust-file`.** A renewal answers with the `garam` server root beside the certificate, and this reads neither that nor the organization issuer: what verifies `garam` is the deployment's to supply, per ADR 0007, and moving it is a decision of its own. That file's contents have moved on the bump above, which is the movement ADR 0007 named the flag for: the listener now presents a leaf signed by a `garam` machine server root, and that root is a separate certificate — measured on 2026-08-26, `CA:TRUE` and five years against the leaf's `CA:FALSE` and ninety days — where ADR 0007 measured a self-signed leaf that was its own root. That narrows the question by a fact without answering it. Not decided here either: what a second operator identity would look like, because one process holds one and nothing needs two.
